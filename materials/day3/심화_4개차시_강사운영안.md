# 3주차 심화 4개 차시 · 강사 운영안

대상: 3·5·6·7차시. 수강생 공개 화면이 아니라 강사의 설명·시연·시간 조절용 문서다. 최신 PPT는 206장으로, 설명이 중복되는 기존 11장을 통합하고 96장의 개념·코드·사례 자료를 추가했다. 모든 장표를 같은 속도로 읽는 방식은 아니다. 페이지별 권장 시간 0분은 선택 참고이며 기본 설명을 대체하거나 빠르게 진행됐을 때 사용한다.

## 1. 하루의 시간과 네 차시의 역할

| 시간 | 차시 | 새로 배우는 핵심 | 코드 실습 | 실행 확인 |
|---|---|---|---:|---:|
| 09:00–09:50 | 1 | 사용자 오류·업무 규칙 | 22분 | 5분 |
| 09:50–10:40 | 2 | Diff·라인·실패 재현 | 25분 | 5분 |
| **10:40–11:30** | **3** | **실제 입력의 차이와 Context 설계** | **25분** | **5분** |
| 11:30–12:00 | 휴식 | 오전 3차시 뒤 30분 | — | — |
| 12:00–13:00 | 점심 | 13시 재개 | — | — |
| 13:00–13:50 | 4 | Codex CLI 호출·검증·오류 복구 | 25분 | 5분 |
| **13:50–14:40** | **5** | **작은 수정·동일 Test·회귀 확인** | **30분** | **5분** |
| 14:40–15:00 | 휴식 | 앞선 2차시 뒤 20분 | — | — |
| **15:00–15:50** | **6** | **State·Node·분기·중단·재개** | **25분** | **5분** |

50분은 이론·시연·직접 실행·확인의 합계다. 자동 Notebook 실행 시간이나 모델 응답 지연으로 50분을 산정하지 않았다. 실제 리허설 시간이 아니므로 학습 속도에 따라 아래 선택 자료로 조절한다.

## 2. 3차시 · 실제 입력의 비교

| 상대 시간 | 구분 | 강사의 진행 | 학생의 실행 |
|---|---|---|---|
| 0–8분 | 이론 | 추론·읽기·실행의 차이, Prompt와 Context | 기존 코드와 제품 정책 대조 |
| 8–14분 | 사례 | Anthropic의 정보 선택, CodeRabbit의 검증 구성 | 업무 규칙이 없을 때 알 수 없는 조건 확인 |
| 14–20분 | 시연 | 세 payload의 실제 필드 비교 | 같은 코드·Diff와 바뀐 필드 구분 |
| 20–30분 | 코드 실습 | 허용 정보 선택 함수와 assert | 정책·Test 제외/포함 조건 실행 |
| 30–40분 | 코드 실습 | 세 Context 생성·Prompt Template 연결 | 요청 파일과 최종 payload 저장 |
| 40–45분 | 코드 실습 | 관련 없는 필드 추가 후 제외 검사 | `unrelated_note` 차단 확인 |
| 45–50분 | 확인 | 다음 차시 CLI 호출에 쓸 입력 확인 | 필드 차이·코드 동일 여부 확인 |

발화 예: “코드만 보고 무료 배송 기준이 할인 전인지 후인지 알 수 있을까요? 모델보다 먼저 입력 자료의 차이를 보겠습니다.”

중요: `review_exercise`는 자동으로 정책을 제공한다. 입력 조건 실험에는 `build_context_payload`·`run_context_review`를 사용한다. 모델 응답 비교는 4차시 연결 후 선택적으로 진행하며, 한 번의 결과를 일반 성능으로 단정하지 않는다.

빠를 때: 저장소 탐색 범위, RAG와 직접 읽기, 주석 속 Prompt Injection, 정책 충돌을 추가 설명한다. 느릴 때: 세 payload의 필드 검사까지 완료하고 live 비교는 강사 결과로 확인한다.

## 3. 5차시 · 단계별 코드 교정

| 상대 시간 | 구분 | 강사의 진행 | 학생의 실행 |
|---|---|---|---|
| 0–5분 | 사례 | Google 리뷰 댓글→수정 제안→사람 적용 | 리뷰와 코드 수정의 차이 |
| 5–10분 | 이론 | Test Oracle·작은 Diff·회귀 확인 | 예상값의 업무 규칙 확인 |
| 10–15분 | 시연 | 재생 모드와 직접 수정 모드 | `APPLY_LEARNER_FIX=False` 선택 |
| 15–25분 | 코드 실습 | 쿠폰 계산·영수증 할인액 두 곳 교정 | 동일 Test 실패 7→5 |
| 25–33분 | 코드 실습 | 할인 후 금액으로 배송 판단 | 동일 Test 실패 5→4 |
| 33–42분 | 코드 실습 | 정수·음수·bool 검증 | 동일 Test 실패 4→0 |
| 42–45분 | 코드 실습 | 경계값 한 개와 실제 영수증 | 3,000원·43,000원 재확인 |
| 45–50분 | 확인 | Test 원본·수정 Diff·남은 문제 | 본인 수정 파일 위치 기록 |

발화 예: “지금 모든 Test가 통과하지 않아도 괜찮습니다. 이번 수정이 쿠폰 오류만 줄였는지, 남은 실패가 무엇인지 설명할 수 있어야 합니다.”

핵심 주의: payable의 상한 한 줄만 고치면 실패는 7→6이다. `coupon_applied_won`도 함께 수정해야 7→5다. 제공 Test의 기대값을 바꿔 통과시키지 않는다. 기본 Run All은 단계별 참고 구현의 자동 재생이므로 직접 코딩 완료와 구분한다.

빠를 때: 파라미터 Test, 금액의 불변 조건, `>=`를 `>`로 바꾸는 Mutation 예제를 별도 복사 파일에서 실행한다. 느릴 때: 수정 힌트로 다음 단계를 이어가되 Test와 실패 이유는 직접 확인한다.

## 4. 6차시 · 직접 조립하는 LangGraph

| 상대 시간 | 구분 | 강사의 진행 | 학생의 실행 |
|---|---|---|---|
| 0–7분 | 이론 | Workflow와 Agent, State·Node·Edge | 고정 처리와 모델 판단 구별 |
| 7–14분 | 이론·사례 | Checkpoint·thread·Sentry 종료 지점 | 승인과 게시의 차이 |
| 14–20분 | 시연 | interrupt 전후 실제 State | 대기 상태 관찰 |
| 20–30분 | 코드 실습 | State·prepare·human 함수 작성 | 직접 정의한 함수 실행 |
| 30–37분 | 코드 실습 | 조건 Edge·END·compile | `build_learner_review_graph` 구현 |
| 37–45분 | 코드 실습 | 같은 thread의 수용·수정·제외 재개 | 분기별 상태 확인 |
| 45–50분 | 확인 | 미결정·잘못된 결정의 처리 | 실제 게시 호출 없음 확인 |

발화 예: “리뷰 생성은 끝났지만 업무는 아직 끝나지 않았습니다. 사람이 판단할 때까지 프로그램이 어디에서 기다리는지 코드로 표현해 보겠습니다.”

순서: State → Node → 분기 함수 → compile → 첫 invoke → `Command(resume=...)`. `human`·`blocked` 등 Notebook의 Node 이름을 그대로 사용한다. 같은 실행을 재개할 때 Graph 객체와 thread 설정을 유지한다.

빠를 때: interrupt 앞부분의 재실행, 메모리와 영속 저장소, 작업 버전·Idempotency를 설명한다. 느릴 때: 완성 Graph import 대신 직접 작성한 Node와 Edge의 최소 경로를 먼저 완성한다.

## 5. 7차시 · 사람이 검증하는 리뷰 평가

| 상대 시간 | 구분 | 강사의 진행 | 학생의 실행 |
|---|---|---|---|
| 0–7분 | 이론 | Test와 Eval, Precision·Recall | 정확한 지적과 누락 구분 |
| 7–14분 | 이론·사례 | Anthropic·OpenAI 평가, 사람 Rubric | 모델 답변과 실제 결과 구별 |
| 14–20분 | 시연 | 4개 결함과 정상 수정본 | 지적 번호·정답 범주 매핑 |
| 20–30분 | 코드 실습 | 사람 판정표 구성 | 실제 Finding별 근거 확인 |
| 30–38분 | 코드 실습 | 중복·미판정·추가 후보 입력 | score 결과의 차이 확인 |
| 38–45분 | 코드 실습 | 정상 코드 Negative Case | 해결된 문제 재지적 여부 확인 |
| 45–50분 | 확인 | 잠정값과 최종값 분리 | live/fixture·미판정 수 기록 |

발화 예: “모델이 네 개를 지적했다고 네 개를 찾은 것은 아닙니다. 같은 오류를 두 번 말했는지, 정말 새로운 결함인지 사람이 연결해 보겠습니다.”

빠를 때: 개발/확인 사례 분리, LLM-as-a-Judge의 한계, LangSmith Annotation Queue 설계를 보충한다. 웹페이지 열람을 코드 실습 시간으로 계산하지 않는다. 느릴 때: 고정 학습 예제로 계산을 익히고 실제 응답은 미판정으로 남긴다. Fixture 결과를 모델 성능이라고 발표하지 않는다.

## 6. 시간이 남거나 부족할 때

- 5분 여유: 해당 차시의 참고 표 1~2장과 구체적인 반례 하나.
- 10분 여유: 별도 입력·잘못된 결정·중복 지적 중 하나를 추가 실행.
- 10분 지연: 선택 자료와 추가 live 호출을 생략. 정책·코드·Test 핵심 순서는 유지.
- 설치 문제: 강사 시연을 보며 코드와 오류를 읽고, 마지막 Q&A에서 복구. 설치 대기를 새 학습 내용으로 세지 않음.
- 학생 발표·짝 활동은 필수 아님. 실행 확인은 개인 화면·자가 assert·선택 질문으로 진행.
