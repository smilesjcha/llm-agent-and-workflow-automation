# 3주차 글로벌 사례와 코드 실험

확인일: 2026-09-06. 공식 문서·공식 연구·개발 회사의 Engineering 공개 자료만 사용했다. 원문의 성과 숫자와 제품 우열 주장은 제외했다. 개별 출처의 확인 범위, 날짜, 한계, 장표용 60–100단어 요약은 [출처 Registry](day3_global_references.json)에 있다.

아래 실험은 회사의 제품 전체를 재현하는 과정이 아니다. 공개된 설계 원리를 교육용 쿠폰 서비스에 적용한 수업 설계다. 웹페이지 열람은 참고 자료 확인이며 코드 실습으로 집계하지 않는다. `기본 실습`은 현재 Notebook/서비스와 연결되고, `선택 확장`은 별도 제작 과제다.

## 차시별 연결

| 차시 | 핵심 사례 | 학생이 직접 할 작업 | 실행·확인 기준 |
|---|---|---|---|
| 3차시 | Anthropic Context·CodeRabbit 팀 기준·Sentry 실행 근거 | 입력 자료 선택 함수<br>Role·Task·Context 구성<br>코드만/규칙 포함/테스트 포함 요청 비교 | 실제 전달 필드의 차이<br>관련 없는 자료 제외<br>모델 호출과 Template 바인딩의 구분 |
| 5차시 | Google 리뷰 수정·CodeRabbit 후보 검증 | 잘못된 줄 번호 차단<br>쿠폰 상한·배송비·입력 검사의 단계적 수정<br>같은 테스트 재실행 | 코드 Diff<br>9개 테스트의 7→5→4→0 실패 변화<br>기존 정상 입력 유지 |

각 차시에 사례 설명을 반복해서 넣지 않는다. `사례의 설계 선택 → 수업 코드의 대응 부분 → 실행 결과`의 한 흐름으로 연결한다. 50분 기본 운영에는 필수 실험을 배치하고, 추가 실제 모델 호출과 서비스 확장은 선택 과제로 둔다.

## 1. 판단 자료의 선택 — 3차시

Anthropic은 Context를 지시문·도구·자료·이력을 포함한 입력 환경으로 설명한다. [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

CodeRabbit의 팀 선호도 관리에서는 파일별 적용 범위와 일회성 예외를 구분한다. [Learnings](https://docs.coderabbit.ai/knowledge-base/learnings)

Sentry는 오류·Trace·로그와 코드의 연결을 실제 디버깅 입력으로 사용한다. [Seer](https://docs.sentry.io/product/ai-in-sentry/seer/)

### 수업 적용

| 구분 | 내용 |
|---|---|
| 먼저 보여줄 차이 | 같은 `checkout.py`에 어떤 자료를 추가했는가 |
| 기본 실습 | `learner_public_context`로 허용 필드 선택<br>`learner_review_prompt`로 요청 MD 작성<br>`build_context_payload`로 실제 전송 자료 구성 |
| 입력 조건 | `code_only`: 코드·Diff<br>`policy`: 코드·Diff·업무 규칙<br>`policy_and_tests`: 앞의 자료·실제 테스트 결과 |
| 확인 코드 | `business_rules`와 `test_evidence`가 선택하지 않은 요청에 없는지 `assert` |
| 선택 확장 | 같은 모델로 두 조건 호출 → 지적을 사람이 비교<br>파일 경로별 기준 선택 함수를 구현하고 적용/미적용 테스트 |
| 파일 | `scripts/build_day3_notebook.py`<br>`labs/day3/review_copilot/deep_dive.py`<br>`labs/day3/review_copilot/fixtures/checkout/requirements.md` |

설명 발화 예시: “같은 코드인데 쿠폰 정책을 모르는 상태와 아는 상태가 다릅니다. 이번에는 모델을 바꾸지 않고, 판단에 필요한 자료 한 종류만 바꿔 보겠습니다.”

기준: Template 생성은 아직 모델 호출이 아니다. 실제 요청 비교에는 `run_context_review`를 사용한다. 기존 `review_exercise`는 자동으로 Context를 구성하므로 엄밀한 입력 조건 비교에 그대로 재사용하지 않는다. `RUN_CONTEXT_COMPARE`와 호출 한도를 확인하고 선택적으로 실행한다. 한 번의 결과만으로 개선을 확정하지 않는다.

## 2. 리뷰 댓글과 최소 수정 — 5차시

Google의 공개 사례는 리뷰 댓글을 수정 제안으로 연결하고 개발자의 미리보기·적용·피드백을 함께 다룬다. [Resolving code review comments with ML](https://research.google/blog/resolving-code-review-comments-with-ml/)

관련 연구의 공식 초록도 리뷰 이후 제안에서 리뷰 중 상호작용으로 발전한 흐름을 설명한다. 확인 범위는 초록이며 논문 전체 실험 분석은 아니다. [Resolving Code Review Comments with Machine Learning](https://research.google/pubs/resolving-code-review-comments-with-machine-learning/)

설계·기능·테스트를 함께 보는 기준은 Google의 공개 코드 리뷰 가이드와 연결한다. [What to look for in a code review](https://google.github.io/eng-practices/review/reviewer/looking-for.html)

### 수업 적용

| 단계 | 코드 작업 | 확인 |
|---|---|---|
| 1. 실패 재현 | 상품 10,000원·쿠폰 15,000원 실행 | 잘못된 결제 예정액과 실패 테스트 |
| 2. 최소 수정 | 쿠폰 상한·영수증 할인액 수정 | 7개 실패 → 5개 실패 |
| 3. 다음 결함 | 할인 후 금액으로 배송비 계산 | 5개 실패 → 4개 실패 |
| 4. 입력 검증 | 음수·소수·bool 입력 검사 | 4개 실패 → 0개 실패 |
| 5. 회귀 확인 | 일반 쿠폰·무료 배송 기준 재실행 | 기존 정상 동작 유지 |

이는 제공된 9개 테스트와 단계별 예제 코드에서 확인하는 교육용 결과다. 모든 Codex 수정이 같은 단계나 같은 결과를 낸다는 뜻은 아니다. 모델이 다른 안전한 수정을 제안하면 동일한 요구사항과 테스트로 판단한다.

학생은 준비된 작업 폴더의 `starter/checkout.py`를 수정한다. 저장소 원본 테스트는 `fixtures/checkout/checkout_checks.py`이며, 준비 과정에서 작업 폴더로 복사된다. `build_stage_source`는 단계별 참고 소스를 반환하는 함수다. 직접 작성할 때는 Notebook의 `APPLY_LEARNER_FIX=False`를 선택하고 해당 단계 조건을 구현한 뒤 셀을 실행한다. 자동 예제 적용은 참고·복구용으로 구분한다.

Codex 요청 예시:

> 이 작업 폴더의 checkout.py에서 쿠폰 상한과 영수증의 실제 적용 할인액만 수정해 주세요. 테스트 파일은 바꾸지 마세요. 먼저 실패 입력과 기대 결과를 확인하고, 최소 Diff와 같은 테스트의 실행 결과를 보여 주세요. 파일 게시나 PR 생성은 하지 마세요.

읽기 전용 리뷰 Adapter와 대화형 Codex의 코드 수정은 별도 단계다. “리뷰를 받았다”와 “코드가 바뀌어 테스트가 통과했다”를 같은 결과로 표현하지 않는다.

## 3. 후보 생성과 코드 검증 — 5차시

CodeRabbit은 Context 구성, 리뷰 후보 생성, 검증, 평가를 분리한 설계를 공개했다. 이는 회사의 자체 Engineering 설명이며 독립 성능 비교는 아니다. [Explainable reviews](https://www.coderabbit.ai/blog/explainable-reviews-coderabbit-review-context-engine)

### 수업 적용

| 입력 | 검사 | 기대 결과 |
|---|---|---|
| 실제 추가 줄의 리뷰 | 파일·줄이 추가된 줄 집합에 존재 | 다음 검토 단계로 전달 |
| 999번 줄의 리뷰 | 파일·줄 조합이 존재하지 않음 | 제거 목록에 기록 |
| 줄은 맞지만 근거가 약한 리뷰 | 재현 입력과 의미적 타당성 | 사람이 수용·수정·제외 판단 |

기본 실습은 `learner_grounded_candidates`를 직접 구현한 뒤 실제 서비스의 `review_engine.py` 처리와 비교하는 것이다. 정상 후보 하나와 잘못된 후보 하나를 직접 구성하고 결과를 확인한다. JSON 출력 자체가 목표가 아니라 조건문·집합 비교가 어떤 후보를 통과시키는지 이해하는 것이 목표다.

설명 발화 예시: “문장이 자연스럽다는 것은 프로그램이 검증할 수 있는 조건이 아닙니다. 지금은 먼저 그 줄이 실제로 존재하는지 검사하겠습니다. 존재한다고 해서 지적까지 맞는 것은 아니므로 다음 확인이 남습니다.”

## 4. 사람 확인과 종료 지점 — 6차시

LangGraph의 재개는 같은 thread의 상태를 이어가며, 중단 노드의 앞부분은 다시 실행될 수 있다. [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

메모리 기반 Checkpointer는 프로세스 재시작 후 상태를 유지하지 않는다. [Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

Sentry의 API는 실행 단계와 중단 지점을 구분한다. [Start Seer Issue Fix](https://docs.sentry.io/api/seer/start-seer-issue-fix/)

### 수업 적용

| 구분 | 기본 실습 | 선택 확장 |
|---|---|---|
| 사람 입력 | 결정·검토자·이유 검증 | 권한 있는 검토자 확인 |
| 상태 유지 | 같은 thread로 `Command(resume=...)` | 새 thread와 새 프로세스 비교 |
| 수정 검토 | 수정된 지적 재검사 | 잘못된 줄 번호 수정안 차단 |
| 종료 정책 | 미결정은 대기·제외는 전달 보류 | 분석 전용 요청에서 게시 호출 횟수 0 검사 |
| 중복 실행 | 승인 뒤 결과 준비 | interrupt 앞 카운터 증가 실험·별도 노드 분리 |

기본 파일은 `labs/day3/review_copilot/langgraph_review.py`와 Notebook 6차시다. 수강생의 진행 중인 커널을 재시작하는 대신 독립적인 작은 스크립트에서 상태 소실을 관찰한다. 메일·PR·결제 같은 실제 외부 변경은 하지 않는다. 외부 게시를 모방한 함수에 호출 횟수만 남겨 승인 전에는 실행되지 않는지 검사한다.

설명 발화 예시: “요약이나 리뷰가 완성됐다는 사실과 외부에 게시해도 된다는 판단은 다릅니다. 이번 요청이 어디까지 허용됐는지 상태로 표현하고, 그 다음 행동이 실행되지 않았다는 것도 테스트하겠습니다.”

## 5. 실제 결과와 회귀 검사 — 7차시

Anthropic은 실행 기록, 최종 결과, 코드 검사와 사람 판정을 나눠 평가하도록 설명한다. [Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

GitHub 역시 AI 리뷰의 누락·오탐·부정확한 수정 가능성을 명시한다. [Application card: GitHub Copilot Agents](https://docs.github.com/en/copilot/responsible-use/agents)

### 수업 적용

| 질문 | 측정 단위 | 주의점 |
|---|---|---|
| 무엇을 찾았는가 | 고유 결함 범주 | 같은 결함을 여러 문장으로 지적해도 한 건 |
| 무엇을 잘못 지적했는가 | 사람의 오탐 판정 | 기준에 없지만 유효한 추가 문제를 자동 오탐 처리하지 않음 |
| 무엇을 놓쳤는가 | 기대 결함 중 미발견 항목 | 지적 수가 많아도 누락 가능 |
| 검토가 끝났는가 | 미판정 항목 수 | 미판정이 남으면 최종 Precision 보류 |
| 실제로 고쳐졌는가 | 코드 실행과 같은 테스트 | 자연어 성공 선언으로 대체하지 않음 |

`checkout_ground_truth()`의 기대 결함 4범주와 테스트 9개는 다른 단위다. 사람용 기준은 모델 요청에 자동으로 섞지 않는다. `score_review_findings(findings, judgments)`에는 사람이 연결한 지적별 판정을 전달한다. Notebook의 간단한 `learner_review_metrics`는 공식 계산 학습용이며 실제 모델의 전체 품질 점수와 구분한다.

Codex 요청 예시:

> 이 평가 코드에서 같은 문제를 두 번 지적해도 TP가 늘어나지 않는지 확인해 주세요. 아직 사람이 확인하지 않은 항목은 오탐으로 단정하지 말고 미판정으로 남겨 주세요. 정상 경우와 중복·미판정 경우의 테스트를 추가하고 실제 결과를 보여 주세요.

## 6. 같은 기준의 사람 평가 — 7차시

LangSmith는 공통 Rubric을 적용하는 단일 결과 평가와 결과 쌍 비교를 제공한다. [Use annotation queues](https://docs.langchain.com/langsmith/annotation-queues)

### 수업 적용

| 평가 항목 | 판정 기준 | 로컬 기록 |
|---|---|---|
| 근거 타당성 | 실제 코드·업무 규칙과 일치 | 판정·근거 줄 |
| 재현 가능성 | 입력과 기대 결과가 명확 | 실행 명령·결과 |
| 수정 적절성 | 최소 변경으로 해결·회귀 없음 | Diff·테스트 |
| 미판정 이유 | 자료 부족·추가 검토 필요 | 남은 확인 사항 |

우선 로컬 CSV 또는 MD에 `run_id`, `prompt_version`, 판정 이유를 남긴다. 웹 기록은 사용자가 선택한 공개 예제에 한해 추가한다. 계정·권한·제공 범위를 확인하지 않은 상태에서 무료 이용이나 특정 화면의 제공을 보장하지 않는다. 자동 승인과 품질 평가는 다르므로 `Human Review 결정`과 `평가 점수`를 별도 필드로 관리한다.

선택 확장은 로컬 평가 기록을 SDK로 feedback에 연결하는 코드 작업이다. 대시보드 방문 자체를 실습 완료로 인정하지 않는다. 외부 서비스가 없어도 로컬 코드와 평가표로 같은 개념을 학습할 수 있어야 한다.

## 제작·검증 기준

- 출처당 원문 인용 없이 짧게 재서술한다. 전체 출처별 설명은 200단어 이내로 유지한다.
- 출처의 실제 기능과 수업용 구현 아이디어를 구분한다. 기능을 만들기 전에는 `선택 확장`이라고 표시한다.
- 상용 제품을 설치하거나 가입해야만 학습이 완료되는 구성을 피한다.
- 모델 호출 전후의 입력과 결과를 구분하고, Fixture 응답을 실제 모델 결과라고 표시하지 않는다.
- 공식 이미지의 재배포 권한은 확인되지 않았다. 이번 정리에서는 외부 이미지 다운로드 없이 독자 제작 Mermaid와 실제 수업 실행 화면을 사용한다.
- Stripe Minions 두 공식 페이지는 본문 확인에 실패했다. 제목과 다른 글의 재인용만으로 내부 설계를 설명하지 않는다.
- OpenAI·Codex 공식 자료는 별도 검증 담당이 관리한다. 이 Registry에 확인하지 않은 OpenAI 제품 사실을 추가하지 않는다.
