# 3일차 강사용 상세교안

## 과정 개요

3일차의 결과물은 `Review Intelligence Service`다. 수강생은 하나의 Python 변경분을 입력해 다음 결과를 직접 만든다.

1. 변경 파일과 추가된 줄을 정확히 읽은 결과
2. 실제 변경 줄에 연결된 구조화된 Review Finding
3. 정적 규칙, Test 결과, 선택 LLM 분석을 합친 Review Report
4. 사람이 Finding을 유지·수정·제외한 Review Decision
5. Golden Set 평가와 Release Gate
6. Localhost 화면과 JSON·Markdown Export
7. Git Branch, Commit, Pull Request, CI, Codex Review로 이어지는 변경 이력

3일차는 GitHub에 자동 Comment를 쓰는 날이 아니다. 실제 외부 서비스 변경과 Idempotency는 4일차에서 다룬다. 오늘은 PR에 올릴 수 있는 코드와 검증 증거를 만들고, 사람의 Merge 판단까지 연결한다.

## 오프닝 Demo

### 6분 시연

1. `meeting_export_pr.diff`를 Localhost 화면에 입력한다.
2. `Review 실행`을 누른다.
3. 변경 파일, Finding, Severity, Evidence Line을 보여준다.
4. 한 Finding을 `유지`, 한 Finding을 `수정`, 한 Finding을 `제외`한다.
5. JSON과 Markdown을 Export한다.
6. GitHub PR에서 CI와 Review Comment가 어디에 남는지 완성 화면으로 보여준다.

### 오프닝 발화

> 오늘 목표는 AI에게 코드가 좋은지 물어보는 것이 아닙니다. 변경 줄, 실제 Test, 저장소 규칙을 근거로 사람이 판단할 수 있는 Review Service를 직접 만듭니다.

> 많이 지적하는 Reviewer보다, 중요한 문제를 정확한 줄에 남기는 Reviewer가 더 유용합니다.

## 1차시 · Review 기준과 Service Architecture

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-6분 | 완성 Service Demo | Localhost Review 화면 |
| 6-18분 | Code Review의 목적과 Finding 기준 | PPT 비교표 |
| 18-28분 | Severity·Confidence·False Positive | `AGENTS.md` |
| 28-44분 | Rubric과 Contract 실행 | Notebook 1차시 |
| 44-50분 | 허용·차단 결과 확인 | `01_review_contract.json` |

### 핵심 설명

- Finding은 한 가지 문제만 다룬다.
- 변경된 줄과 사용자 영향이 연결되지 않으면 Finding이 아니다.
- Formatting과 단순 Style은 Linter에 맡긴다.
- P0~P3는 말투의 강도가 아니라 영향과 복구 난이도로 정한다.
- Confidence가 낮은 결과는 게시 후보가 아니라 사람 확인 대상으로 남긴다.

### Severity 기준

| 등급 | 의미 | 예시 |
|---|---|---|
| P0 | 즉시 악용, 심각한 데이터 손실, 임의 코드 실행 | 외부 입력을 `eval()`로 실행 |
| P1 | 외부 상태 변경, 핵심 기능 장애, 권한 우회 | 승인 없는 API Write |
| P2 | 복구 불가, 관측 불가, 반복 운영 오류 | 넓은 Exception으로 원인 소실 |
| P3 | 좁은 범위의 유지보수 문제 | 중복 처리, 불명확한 Error Message |

### 강사 시연

Notebook 1차시 Cell을 실행해 `ReviewPolicy`와 `ReviewFinding`의 계약을 먼저 보여준다. 화면에서 `path`, `line`, `severity`, `evidence`, `correction`, `rule_id`를 차례로 짚고 자동 게시 필드가 `false`인지 확인한다.

### 수강생 소프트웨어 실습

1. Notebook 1차시 Cell을 실행한다.
2. `P1` 설명을 자신의 업무 맥락으로 한 줄 보완한다.
3. 허용 `ReviewFinding`의 필드와 Pydantic `extra=forbid` 계약을 확인한다.
4. `severity=P5`를 넣어 `FINDING_SEVERITY_INVALID`를 확인한다.
5. 결과 JSON을 저장한다.

### 완료 기준

- Finding 필수 필드를 설명할 수 있다.
- 허용 Contract가 통과한다.
- 잘못된 Line 또는 자동 게시 요청이 구조화된 실패로 끝난다.

## 2차시 · Unified Diff와 Line Mapping

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-10분 | Diff·Hunk·Old Line·New Line | 실제 Fixture Diff |
| 10-22분 | Hunk Header 해석 | `@@ -8,5 +8,11 @@` |
| 22-30분 | Parser Code Walkthrough | `diff_parser.py` |
| 30-45분 | Parser 수정과 Test | Notebook·Terminal |
| 45-50분 | Line Mapping 확인 | `02_parsed_diff.json` |

### 핵심 설명

```text
context line : old +1, new +1
deleted line : old +1
added line   : new +1, Review 대상
```

`+++` Header의 `+`와 Code Addition의 `+`를 구분한다. Hunk 밖의 Text를 Code로 인식하지 않는다. Absolute Path와 `..` Segment를 차단한다.

### 강사 시연

```bash
python -m pytest -q tests/test_day3_review_copilot.py -k "diff or line"
```

먼저 기본 Mapping을 보여준 뒤 다음 실패를 순서대로 실행한다.

- 빈 Diff
- Hunk가 없는 Text
- `/tmp/secret.py` Absolute Path
- `../../secret.py` Path Traversal
- 삭제만 있는 Hunk

### 수강생 소프트웨어 실습

1. `meeting_export_pr.diff`에서 추가된 줄 번호를 손으로 먼저 계산한다.
2. `learner_added_line_map()`을 직접 작성해 손 계산과 비교한다.
3. 두 번째 Hunk가 있는 학습용 Diff를 실행한다.
4. 정본 Parser와 직접 작성한 함수의 결과를 대조한다.
5. 잘못된 Path Fixture가 `DIFF_PATH_BLOCKED`로 끝나는지 확인한다.
6. Parser 결과를 JSON으로 저장한다.

### 완료 기준

- Review Comment가 New Line을 사용하는 이유를 설명한다.
- 기본 Fixture의 Added Line이 정확히 복원된다.
- Path Escape가 Raw Traceback 대신 Stable Error Code로 끝난다.

## 3차시 · Context Selection과 Data Boundary

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-10분 | 전체 Repository와 Review Context의 차이 | Context 비교 |
| 10-22분 | Call Site·관련 Test·정책 문서 | `rg` 결과 |
| 22-30분 | Workspace·Secret·Size Boundary | Context Builder |
| 30-45분 | Context Pack 제작 | Notebook 3차시 |
| 45-50분 | 제외 근거 확인 | `03_context_pack.json` |

### 핵심 설명

Context를 많이 넣는다고 정확도가 자동으로 높아지지 않는다. Review에 필요한 최소 문맥은 다음 순서로 선택한다.

1. Changed Path
2. Changed Symbol 주변 Code
3. 직접 호출부
4. 관련된 Focused Test
5. 가까운 `AGENTS.md`

다음 항목은 기본 제외다.

- `.env`와 Secret 형태 Text
- `.git`, Cache, Build, Generated Output
- Workspace 밖 Path
- 최대 Byte를 넘는 대형 File
- 변경과 관계없는 고객 데이터

### 강사 시연

```bash
rg -n "run_review_workflow|ReviewFinding" labs/day3 tests
```

이후 Notebook 3차시 Cell에서 allowlist 결과, `private_customer_note` 제외, workspace 밖 경로 차단을 이어서 보여준다.

### 수강생 소프트웨어 실습

1. Context Allowlist를 확인한다.
2. `learner_public_context()`로 허용 Field만 직접 선택한다.
3. Changed Path와 가까운 실제 Test Candidate를 수집한다.
4. `.env` 요청을 넣어 제외 이유를 확인한다.
5. 최대 Byte를 작게 바꿔 `CONTEXT_BUDGET_EXCEEDED`를 재현한다.
6. 허용 File과 제외 File을 결과에 함께 기록한다.

### 완료 기준

- Context Pack에 포함한 이유와 제외한 이유가 함께 남는다.
- Workspace 밖 File을 읽지 않는다.
- 실제 Secret 값은 Notebook Output과 Trace에 남지 않는다.

## 4차시 · Structured Output과 Provider Adapter

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-10분 | 자유 문장과 Structured Output | JSON 비교 |
| 10-20분 | Prompt Input·Schema·Parser | LangChain 구성 |
| 20-28분 | Fixture·Ollama·OpenAI Adapter | Provider Contract |
| 28-44분 | Candidate Review 실행 | Notebook 4차시 |
| 44-50분 | Fallback 확인 | `04_candidate_review.json` |

### 핵심 설명

LangChain은 Prompt, Model Adapter, Parser를 같은 입출력 계약으로 연결한다. Provider가 바뀌어도 아래 결과 필드는 바뀌지 않는다.

```text
provider_requested
provider_used
status
findings
fallback_reason
automatic_publish=false
```

### Provider 운영 기준

| Provider | 기본 사용 | 실패 시 동작 |
|---|---|---|
| Fixture | 항상 가능 | 같은 입력에 같은 결과 |
| Ollama | 명시적 Opt-in | 원인 기록 후 Fixture 가능 |
| OpenAI | 명시적 Opt-in·Local `.env` | 원인 기록 후 Fixture 가능 |

Live 실행 결과와 Fixture 결과를 같은 것으로 표시하지 않는다. API Key는 출력·캡처·Commit하지 않는다. Fixture 기반 `rule_baseline_gate`가 통과해도 Live Candidate 자체의 품질을 증명하지는 않는다. Live Candidate 전용 평가가 없으면 `provider_candidate_gate=HOLD`를 유지한다.

선택 설치는 Core와 분리한다.

```bash
python -m pip install -r requirements-local-llm-optional.txt
python -m pip install -r requirements-openai-optional.txt
```

### 수강생 소프트웨어 실습

1. Fixture Adapter로 Candidate Finding을 생성한다.
2. 연결 불가 OpenAI adapter가 fixture로 바뀔 때 provenance를 확인한다.
3. Provider를 `ollama`로 바꾸되 Opt-in이 없을 때는 live call을 실행하지 않는다.
4. 준비된 수강생만 `RUN_OPTIONAL_LIVE_PROVIDER=True`로 Local Model을 실행한다.
5. Provider Contract를 JSON으로 저장한다.

### 완료 기준

- Provider 교체 후에도 같은 Schema를 사용한다.
- Live 실행 여부와 Fallback 이유가 보인다.
- Schema를 통과하지 못한 Finding은 다음 단계로 넘어가지 않는다.

## 5차시 · Hybrid Review Pipeline

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-10분 | Static·Test·LLM 역할 분리 | 역할 비교표 |
| 10-20분 | Deduplication·Ranking | Rule ID·Evidence Key |
| 20-28분 | Pipeline Code Walkthrough | `workflow.py` |
| 28-44분 | 대표 Diff와 Focused Test 결합 | Notebook 5차시 |
| 44-50분 | 통합 Report 확인 | `05_hybrid_review.json` |

### 역할 분리

| 단계 | 잘하는 일 | 결과 |
|---|---|---|
| Static Rule | 반복 가능한 위험 Pattern | 정확한 Line과 Rule ID |
| Focused Test | 실제 Behavior 검증 | Command, Exit Code, Output |
| LLM | 의미와 영향 설명, 누락 후보 | Structured Candidate |
| Human | 사실성, 중요도, 조직 맥락 판단 | Keep·Edit·Drop |

### 강사 시연

```bash
python -m pytest -q tests/test_day3_review_copilot.py -k "workflow or evidence"
```

### 수강생 소프트웨어 실습

1. 대표 Diff의 Static Finding과 Candidate Finding을 분리해 확인한다.
2. Focused Test의 실제 Exit Code를 Review evidence에 결합한다.
3. `learner_grounded_candidates()`를 직접 작성해 존재하지 않는 Line 후보를 제거한다.
4. 같은 `path + line + rule_id` Finding을 한 건으로 합친다.
5. Test를 실행하지 않은 상태가 `READY`가 되지 않는지 확인한다.
6. Summary Report를 저장한다.

### 완료 기준

- 실행하지 않은 Test를 Passed로 기록하지 않는다.
- 하나의 위험을 중복 Finding으로 남기지 않는다.
- LLM 실패가 Static Finding을 지우지 않는다.

## 6차시 · LangGraph와 Human Review

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-10분 | State·Node·Edge·Checkpoint | Workflow Diagram |
| 10-20분 | Interrupt Payload와 Thread ID | 실행 JSON |
| 20-28분 | Keep·Edit·Drop 상태 전이 | Decision Table |
| 28-44분 | Interrupt·Resume 실행 | Notebook 6차시 |
| 44-50분 | 외부 서비스 변경 차단 확인 | `06_human_review.json` |

### Graph State 최소 필드

```text
draft
findings
review
audit
status
external_write=false
```

### 수강생 소프트웨어 실습

1. Graph를 시작하고 Interrupt에서 멈춘다.
2. Payload의 Diff Target, Finding, Evidence, 선택지를 읽는다.
3. 유지(`approve`), 수정(`edit`), 제외(`reject`) 중 하나를 선택한다.
4. 같은 `thread_id`로 한 번만 Resume한다.
5. 최종 State와 Audit Log를 확인한다.
6. 같은 `REVIEW_DECISION`을 8차시 Workflow에 전달한다. `reject`는 GitHub 계획과 Release를 `HOLD`로 유지한다.

### 주의

- 하나의 완료된 Thread로 세 Decision을 연속 실행하지 않는다.
- Interrupt를 일반 Exception으로 잡지 않는다.
- Resume 전 외부 Comment나 Merge를 실행하지 않는다.
- Notebook에서는 Memory Checkpointer를 사용한다.

### 완료 기준

- Interrupt 상태와 Resume 상태를 구분한다.
- 선택한 Decision이 최종 상태와 Audit Log에 남는다.
- 모든 Case에서 `external_write=false`다.

## 7차시 · Golden Set과 Review Eval

### 50분 구성

| 구간 | 내용 | 화면 |
|---|---|---|
| 0-12분 | Golden Set과 평가 단위 | Case Manifest |
| 12-22분 | Precision·Recall·F1 | 작은 숫자 예제 |
| 22-30분 | Release Gate | Threshold Table |
| 30-44분 | Baseline·Candidate 비교 | Notebook 7차시 |
| 44-50분 | 오류 분석 | `07_evaluation.json` |

### 평가 Key

Finding 문장 전체가 아니라 안정적인 Key를 사용한다.

```text
case_id + path + line + rule_id
```

### 평가 해석

- Precision이 낮으면 불필요한 지적이 많다.
- Recall이 낮으면 잡아야 할 위험을 놓친다.
- F1은 두 값의 균형을 본다.
- P0·P1 Miss는 평균 점수와 별도로 Release를 막는다.
- Clean Case에서 Finding이 생기면 False Positive로 기록한다.

### 수강생 소프트웨어 실습

1. 8개 Case와 Golden Finding을 불러온다.
2. `learner_review_metrics()`를 직접 작성하고 Baseline 수치와 대조한다.
3. 안전한 Negative Case의 False Positive가 0인지 확인한다.
4. 예상 Parser Failure가 같은 Error Code로 처리되는지 확인한다.
5. Release Gate의 `READY` 기준을 확인한다.

### 완료 기준

- Metric 계산의 분모를 설명할 수 있다.
- 점수와 Error Case 목록이 함께 남는다.
- P0·P1 Miss가 있는 결과는 자동 Release하지 않는다.

### Git 명령

첫 원격 제출은 `Draft PR`로 고정하고, CI와 사람 리뷰 뒤에만 Ready 전환 여부를 결정한다.

```bash

```

PR Comment에서 Codex Review 연결이 완료된 저장소만 다음을 사용한다.


자동 Review가 준비되지 않은 환경에서는 PR Diff를 Codex Desktop에 열고 동일한 Review Criteria를 입력한다. 어느 경로든 Test·CI·AI Review는 Human Merge를 대체하지 않는다.

### Codex·Claude Code 선택 비교

두 도구가 같은 Working Tree를 동시에 수정하지 않게 한다. Codex branch의 Diff·Test를 먼저 보존하고, `main`에서 다시 분기한 Claude branch에 동일한 `CODEX_TASK.md` 요청을 주어 비교한다.

| 비교 축 | 확인 증거 |
|---|---|
| 범위 준수 | 허용한 Path 밖 변경 0건 |
| 허용·차단 동작 | 같은 Focused Test의 실제 종료 코드 |
| 근거 품질 | 실제 Added Line과 Rule ID 연결 |
| Diff 품질 | 최소 변경·이해 가능한 이름·정책 설명 |
| 권한 보호 | Secret 미포함·`external_write=false`·자동 Merge 없음 |

비교 결과는 모델 순위가 아니라 `어떤 Harness가 재현 가능한 결과를 만들었는가`로 정리한다.

### 완료 기준

- Localhost Service가 Fixture로 동작한다.
- 변경 범위와 Test 증거가 PR에 보인다.
- CI 결과와 AI Review를 구분한다.
- Merge는 실행하지 않고 사람 판단 상태로 남긴다.

## 8시간이 가능한 이유

3일차는 한 번의 코드 생성 Demo를 길게 늘인 구성이 아니다. 각 차시는 이전 결과를 다음 입력으로 사용하며 서로 다른 실패 지점을 직접 다룬다.

| 차시 | 새로 추가되는 기능 | 대표 실패 |
|---|---|---|
| 1 | Review Contract | 잘못된 Severity·자동 게시 |
| 2 | Diff Parser | Line Mapping·Path Escape |
| 3 | Context Builder | Secret·대용량·Workspace 이탈 |
| 4 | LLM Adapter | Schema Error·Provider Fallback |
| 5 | Hybrid Orchestrator | 중복 Finding·미실행 Test |
| 6 | Human Review Graph | 잘못된 Thread·승인 누락 |
| 7 | Evaluation | False Positive·P0 Miss |
| 8 | Localhost·GitHub Harness | Scope 이탈·CI 실패·자동 Merge 위험 |

동일한 개념을 반복 설명하지 않는다. 1차시의 Rubric은 4차시 Contract, 5차시 Ranking, 7차시 Evaluation에서 입력으로 재사용한다. 2차시의 Line Mapping은 5차시 Finding과 8차시 PR Review의 근거가 된다.
