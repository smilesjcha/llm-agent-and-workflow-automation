# 3일차 강사용 상세교안 · 코드 리뷰 Agent

## 이번 개편의 중심

수강생은 잘못 계산되는 주문 서비스를 실행하고, 실패 Test를 읽고, 코드 리뷰를 받고, 직접 코드를 고친다. 마지막에는 수정 전후를 같은 입력으로 검증한다. 결과 JSON을 만드는 것은 서비스 구현의 중간 단계이며 수업의 완료 기준은 아니다.

수업 결과는 ① 실행 가능한 주문 코드 ② 수정 전 실패와 수정 후 Test ③ 근거 있는 리뷰 Markdown ④ 사람의 편집 결과 ⑤ 같은 코드가 연결된 Localhost 화면이다.

강사의 진행 의도·시간 조절·검증 기준은 이 문서에서만 관리한다. 수강생 PPT에는 현재 개념·실행 명령·코드·예상 결과·다음 단계를 보여준다.

## 원안과 1·2주차의 연결

원안은 6개 모듈의 40시간이며 주차별 5개 모듈이 아니다. 1주차는 Agent·Tool Calling·실행 권한·환경·STT 입문, 2주차는 회의기록 입력 변환·맥락·문서·코딩 Agent·LangGraph·Localhost를 실제로 다뤘다. 3주차에서는 같은 흐름을 코드 리뷰라는 다른 문제에 적용한다.

| 앞선 내용 | 3주차의 새 적용 | 반복하지 않을 설명 |
|---|---|---|
| Tool Calling·실행 권한 | 대화형 Codex의 읽기·수정·Test, Python Adapter의 제한된 호출 | 도구 호출의 정의 전체 반복 |
| 회의 원문의 근거 | 코드의 파일·추가 줄·실제 Test | 근거 중요성을 추상적으로 재설명 |
| 산업·회의 맥락 | 주문·쿠폰·배송비 업무 규칙 | Context의 긴 일반론 |
| 사람 승인 | 실제 interrupt·리뷰 제목 편집·거절 시 제외 | 승인 필요성만 강조하는 장표 |
| Localhost | 방금 수정한 파일을 화면에 연결 | 서비스 홈페이지 열람 |

원안 시간의 대응은 1주차 모듈1 6H+모듈2 2H, 2주차 모듈2 4H+모듈5 4H, 3주차 모듈3 8H, 4주차 모듈4 6H+모듈5 2H, 5주차 모듈5 2H+모듈6 6H다. 이 표는 주제 누락을 막는 교육 설계 기준이며, 1·2주차 발화 시간을 사후 측정한 수치가 아니다.

## 강의 전 준비

학생은 `git clone --branch codex/day3-review-intelligence https://github.com/smilesjcha/llm-agent-and-workflow-automation.git`로 개편 branch를 받거나 학생용 ZIP을 사용한다. main의 이전 버전과 구분한다. 기존 수정 중인 학생 저장소는 덮어쓰지 않고 새 폴더에 받도록 안내한다.

ZIP에는 PPT·PDF·실행 결과 Notebook이 포함되지 않으므로 별도 배포한다. ZIP의 준비 검사는 `python scripts/run_day3_preflight.py --code-only`를 사용한다. 이 모드는 Git을 필수로 검사하지 않으므로 2차시 전에 `git --version`을 추가 확인한다. 5차시 코드 수정 후 앞의 리뷰 셀을 역순 재실행하지 않고, 복습은 새 폴더를 만드는 Run All로 진행한다.

```bash
python -m pip install -r requirements-day3.txt
codex --version
codex login status
python scripts/run_day3_preflight.py
python -m pytest -q tests/test_day3_review_copilot.py tests/test_day3_notebook.py
```

로그인되지 않았으면 강사가 터미널에서 `codex login`을 진행한다. 실제 인증값은 화면·Notebook·Git에 남기지 않는다. 수업용 Adapter는 `--ignore-user-config`로 개인 설정을 제외한 CLI 기본 모델을 사용한다. 필요하면 `CodexCLIReviewProvider(model=...)`로 계정에 허용된 모델을 명시한다. Local CLI는 PC 프로그램 실행 위치이며 모델 추론은 네트워크를 사용한다. 계정별 사용 가능 범위는 당일 확인한다.

학생의 주 실행 경로는 **`RUN_CODEX_LIVE=True`**다. 기본 `False`는 복습용 전체 실행에서 제공된 예제 리뷰를 사용하기 위한 설정이다. 이 값을 수업에서 반드시 눈에 띄게 짚고 바꾼다. live 실패는 오류로 남기며 예제 성공으로 자동 바꾸지 않는다.

## 1차시 · 주문 서비스와 리뷰 기준

### 첫 8분 시연

1. 상품 10,000원·쿠폰 15,000원을 초안 서비스에 입력한다.
2. 최종 금액 -2,000원과 실패 Test를 보여준다.
3. 수정된 버전에서는 상품 금액 0원·배송비 3,000원임을 보여준다.
4. 50,000원·쿠폰 10,000원은 40,000원→43,000원으로 바뀌는 두 번째 사례를 보여준다.
5. 리뷰의 파일·줄·재현 조건이 실제 수정으로 연결된 화면을 보여준다.

발화: “정상 주문만 넣으면 문제가 보이지 않습니다. 오늘은 고객이 실제로 넣을 수 있는 조건에서 오류를 찾고 고칩니다.”

### 이론 15분

업무 규칙·회귀 오류·Finding·Severity를 이 사례로 설명한다. 결함의 증거는 말투나 자신감이 아니라 재현 입력·사용자 영향·코드 위치다. Linter가 처리할 문체와 사람이 확인할 기능 오류를 비교한다.

### 코드 실습 22분

학생은 `learner_payable()`을 입력하고 정상·초과 쿠폰 결과를 비교한다. 이어서 실제 `starter/checkout.py`와 `checkout_checks.py`를 실행한다. 9개 중 7개 실패가 의도된 결과임을 먼저 안내한다. 실패 메시지에서 실제값·기대값을 손으로 가리키게 한다. 공개 발표는 요구하지 않는다.

### 확인 5분

화면에서 입력 10,000/15,000, 실제 -2,000, 기대 3,000, 실패 Test를 연결한다. 시간이 남으면 `coupon=total`을 추가하고, 부족하면 이 핵심 재현까지 확보한다.

## 2차시 · Git Diff와 변경 줄

### 이론 13분·시연 7분

`+++` 파일 헤더와 `+` 코드 추가를 구분한다. Hunk의 앞 숫자는 이전 파일, 뒤 숫자는 새 파일의 시작 줄이다. 삭제 줄은 새 줄 번호를 증가시키지 않는다. 리뷰는 변경 후 위치를 가리킨다.

발화: “좋은 지적도 다른 줄에 붙으면 리뷰어가 확인하기 어렵습니다. 오늘의 Parser는 리뷰의 위치를 정확하게 만드는 부품입니다.”

### 코드 실습 25분

`learner_added_line_map()`을 직접 입력한다. 먼저 하나의 변경, 다음으로 떨어진 두 Hunk를 처리한다. 두 번째 Hunk 시작값을 일부러 잘못 넣으면 테스트가 실패하는 과정을 보여준다. 정본 `parse_unified_diff()`와 결과를 대조하고 실제 `git diff --no-index`를 실행한다.

### 확인 5분

3행·11행 Test와 경로 차단을 확인한다. 단순 학습 Parser가 Git의 모든 형식을 지원한다고 설명하지 않는다. rename·binary 등은 정본의 지원 범위와 별도 처리 대상으로 남긴다.

## 3차시 · 리뷰 맥락과 Prompt

### 이론 15분·시연 7분

Role·Task·Context·근거·출력 형식을 설명한다. 학생이 이미 배운 Prompt 기본기를 주문 규칙으로 적용한다. 전체 저장소를 넣는 대신 관련 코드·Test·정책을 선택하는 이유를 사례로 설명한다. 코드 주석은 분석 자료이지 실행 지시가 아니다.

발화: “배송비 기준은 Python 문법에서 나오지 않습니다. 모델이 모르는 서비스의 약속을 우리가 제공해야 합니다.”

### 코드 실습 23분

`learner_public_context()`로 세 필드만 선택한다. 관계없는 합성 메모가 제외되는지 assert로 확인한다. `learner_review_prompt()`로 baseline/refined 요청을 만든다. LangChain `ChatPromptTemplate` 변수에 실제 요청을 연결하고, 이 메시지가 다음 차시의 CLI 입력으로 전달됨을 보여준다.

### 확인 5분

두 Prompt 파일을 열고 바뀐 부분을 비교한다. 수정 정답을 미리 전달해 점수를 높이는 방식과 업무 규칙을 전달하는 방식을 구분한다. 이 차시는 요청 작성이며 아직 모델 호출이 아니다.

## 4차시 · Local Codex CLI 연동

### 이론 12분·시연 8분

설치·로그인·모델 선택·CLI 프로세스·표준입력·종료코드·Timeout·Schema를 설명한다. CLI Adapter는 도구 사용을 끄고 전달된 Context를 분석한다. 대화형 Codex는 사용자가 정한 범위에서 파일 읽기·수정·Test 실행을 할 수 있다. 두 경로를 아키텍처에 따로 표시한다.

발화: “상위 모델에 판단을 맡기는 것과 프로그램의 실행 절차를 맡기는 것은 구분합니다. 이 Adapter는 리뷰 내용에 집중하고 파일·Test·승인은 우리가 만든 코드가 처리합니다.”

### 코드 실습 25분

버전·로그인 상태를 확인한다. `RUN_CODEX_LIVE=True`로 바꿔 실제 호출하고 Markdown을 확인한다. `messages[1].content`가 `review_instructions`로 전달되는 코드를 가리킨다. 학생은 같은 코드에서 업무 규칙 한 문장을 보완해 리뷰 차이를 확인한다. 문자열 shell 실행 대신 인자 배열을 쓰는 이유를 한 예로 설명한다.

### 확인 5분

사용 Provider·파일·줄·영향·수정안을 확인한다. live 실패는 원인에 맞게 복구한다. 시간이 지연되면 학생이 직접 예제 경로를 선택하고 나머지 코딩을 계속한다. 이를 실제 AI 성공으로 표현하지 않는다.

## 5차시 · 리뷰 반영과 회귀 Test

### 이론 10분·시연 8분

Grounding은 실제 코드 줄과 근거에 연결하는 확인이다. 없는 999번 줄 리뷰를 제외한다. 최소 수정과 회귀 Test를 설명하고, 테스트 기대값을 낮추지 않은 상태에서 코드를 고치는 과정을 보여준다.

### 코드 실습 27분

1. `learner_grounded_candidates()` 직접 구현·없는 줄 제외 Test
2. VS Code에서 이번 실습의 `starter/checkout.py` 열기
3. `validate_money()`·`payable()`·배송비 계산 직접 수정
4. 동일 `checkout_checks.py` 재실행
5. 49,999/50,000 배송비 경계·음수 입력 추가 검증
6. 수정 전후 Diff와 주문 결과 비교

발화: “AI가 수정했다는 문장보다 같은 입력에서 달라진 결과와 테스트가 더 분명한 증거입니다.”

### 확인 5분

9개 Test 통과, 첫 사례 3,000원, 두 번째 43,000원을 확인한다. 빠른 학생은 새 경계 조건을 추가한다. 느린 학생은 Notebook 완성 예시를 적용하되 세 변경의 이유를 하나씩 설명하며 진행한다.

## 6차시 · LangGraph 리뷰 승인

### 이론 15분·시연 7분

State·Node·Edge·Checkpoint·Interrupt를 실제 리뷰 상태에 대응한다. LangGraph는 Workflow 상태를 관리하며, 이 자체가 자유롭게 도구를 고르는 Agent와 같은 뜻은 아니다.

### 코드 실습 23분

`learner_review_decision()`을 직접 작성한다. Graph 시작 셀에서 `REVIEW_REQUIRED`·`__interrupt__`를 확인하고 멈춘다. 다음 셀에서 `edit`와 수정 제목을 입력해 `Command(resume=...)`로 재개한다. 별도 thread에서는 `reject`를 선택해 리뷰가 제외되는 것을 확인한다. 실제 CLI 결과가 있으면 그 리뷰를 사용하고, 없으면 Graph 학습용 예제임을 명시한다.

### 확인 5분

수정된 제목이 최종 Markdown까지 반영되는지 확인한다. `reject`가 마지막 게시 준비를 `HOLD`로 만드는지 확인한다. 화면의 버튼 모양보다 상태 변화가 실제 실행되었는지를 설명한다.

## 7차시 · 리뷰 품질 비교

### 이론 12분·시연 8분

오탐·미탐·Precision·Recall·F1을 작은 표로 계산한다. 평가 사례와 실행 조건을 같게 유지해야 비교할 수 있다. 모델이 붙인 임의 rule ID를 정답과 그대로 비교하면 잘못 채점될 수 있으므로 재현 조건과 위치를 사람이 연결한다.

### 코드 실습 25분

`learner_review_metrics()` 구현 후 정답·오탐·미탐·빈 결과를 넣는다. 예제 baseline과 개선 후보의 점수 변화를 확인한다. 이 점수는 고정 학습 예제임을 장표와 출력에서 명시한다. 시간이 허용되면 같은 Prompt 비교를 실제 CLI로 재실행하고 실제 후보를 별도 채점한다.

### 확인 5분

학생이 오탐 하나를 추가했을 때 어떤 지표가 변하는지 확인한다. 전체 품질을 단일 숫자로 결론내리지 않고 중요한 누락·실행시간·대상 사례 수를 함께 본다.

## 8차시 · Localhost와 다음 서비스

### 이론 10분

1분: Notebook 함수가 HTTP 요청 뒤에서 실행되는 관계. 9분: 4주차 PR 연동6차시+문서 통합2차시, 5주차 문서2차시+통합 운영3차시+개인 프로젝트3차시 안내.

### 시연 8분·코드 실습 27분

Notebook이 출력한 `--exercise-dir` 포함 명령으로 서버를 실행한다. 학생이 방금 수정한 파일을 화면과 HTTP에서 실행한다. `RUN_LOCALHOST_SMOKE=True` 요청이 같은 결과를 내는지 확인한다. 최근 리뷰를 불러오고 Markdown을 열어 편집 결과를 확인한다.

```bash
python -m labs.day3.review_copilot.web --exercise-dir 이번실습폴더 --port 8765
```

구체적인 이번실습폴더는 Notebook 출력값을 쓴다. 경로를 생략한 기본 시연 서비스와 혼동하지 않는다. 서버가 쓰는 Python과 Notebook Kernel이 같아야 한다.

### 확인 5분

코드·Test·리뷰 파일 위치와 재실행 명령을 확인한다. 4주차에 같은 코드를 본인 저장소의 Draft PR로 연결할 예정이다. 5주차 15:00~18:00의 미니 프로젝트는 제작·검증150분+휴식·Q&A30분이다. 입력1종·기능1개·실패조건1개·화면1개를 목표로 한다.

## 시간 조절

| 상황 | 조절 방법 |
|---|---|
| 학생이 빠름 | 새 경계 Test·두 번째 Hunk·Prompt 한 조건 비교·리뷰 하나 제외 |
| 설치가 지연 | 예제 리뷰를 명시적으로 선택하고 실제 Python 수정은 계속 진행 |
| CLI 사용량 제한 | 이미 실행한 실제 리뷰를 강사가 보여주고 학생은 예제로 구현 연결 |
| 코드 입력이 느림 | 완성 예시 적용 후 변경 세 줄과 대응 Test를 직접 설명 |
| 마지막 10분 부족 | 원격 PR 생성은 4주차 계획대로 진행, 오늘은 Localhost·재실행 확인 |

슬라이드 수로 시간을 채우지 않는다. 설명→작동 시연→학생 코드 입력→실패 메시지 해석→수정→재실행에 시간이 필요하므로 각 차시 50분의 근거가 생긴다. 긴 일반론과 중간 요약 반복은 생략한다.
