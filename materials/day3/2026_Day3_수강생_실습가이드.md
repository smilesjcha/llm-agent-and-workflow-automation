# 3일차 수강생 실습가이드

## 오늘 만드는 서비스

`Review Intelligence Service`는 Git Diff를 읽고 변경된 줄에만 Review Finding을 만든다. 정적 규칙과 Test 결과를 먼저 확인하고, 선택적으로 LLM Candidate를 더한다. 최종 Finding은 사람이 유지·수정·제외한 뒤 JSON과 Markdown으로 저장한다.

오늘은 실제 PR Comment나 Merge를 자동 실행하지 않는다.

## 먼저 보는 용어

| 표현 | 이 수업에서의 뜻 |
|---|---|
| Finding | 코드의 문제 하나와 위치·영향·근거·최소 교정을 묶은 리뷰 항목 |
| Context Pack | 변경 코드를 판단하는 데 필요한 코드·Test·정책만 골라 담은 자료 묶음 |
| Fixture | API·Token·Network 없이도 매번 같은 결과를 내는 교육용 입력과 정답 |
| Dry-run | 실제로 게시하지 않고 대상·본문·명령만 미리 만드는 실행 |
| Release Gate | 평가·Test·사람 확인 조건으로 다음 단계 진행 여부를 결정하는 기준 |
| 외부 서비스 변경 (`external_write`) | GitHub Comment·Notion 문서·이메일처럼 내 PC 밖의 상태를 바꾸는 동작 |

## 1차시 · Review Contract

1. Notebook의 `1차시` 제목을 찾는다.
2. 허용 Policy와 Finding field를 확인한다.
3. `severity=P5`를 입력한 실패 조건 실험을 실행한다.
4. `FINDING_SEVERITY_INVALID`가 표시되는지 확인한다.
5. 허용 Contract를 `01_review_contract.json`에 저장한다.

확인:

```text
path
line
severity
evidence
correction
rule_id
automatic_publish=false
```

## 2차시 · Diff Parser

```bash
python -m pytest -q tests/test_day3_review_copilot.py -k "diff or line"
```

1. `+++`에서 변경 File을 찾는다.
2. `@@`에서 Old·New 시작 Line을 읽는다.
3. Context·삭제·추가 Line의 Counter 변화를 확인한다.
4. `learner_added_line_map()`을 직접 실행해 두 개 Hunk의 새 Line 번호를 계산한다.
5. Absolute Path와 `..` Path가 차단되는지 확인한다.
6. Parser 결과의 Line을 원본 Diff와 대조한다.

## 3차시 · Context Builder

1. Changed Path를 입력한다.
2. `learner_public_context()`의 명시적 Allowlist를 직접 작성한다.
3. 가까운 Test Candidate와 실제 존재하는 Test를 확인한다.
4. `private_customer_note`가 결과에서 제외되는지 확인한다.
5. Workspace 밖 경로가 `WORKSPACE_PATH_BLOCKED`로 차단되는지 확인한다.
6. 선택 확장에서 Context Byte Limit를 작게 바꿔 `CONTEXT_BUDGET_EXCEEDED`를 재현한다.

실제 `.env` 내용은 열거나 출력하지 않는다.

## 4차시 · Provider Adapter

기본 Fixture는 Notebook의 4차시 Cell을 실행한다. `provider_requested=fixture`, `provider_used=fixture`를 먼저 확인한다.

선택 Ollama:

```bash
ollama list
ollama pull qwen3:4b
python -m pip install -r requirements-local-llm-optional.txt
```

OpenAI 선택 경로는 `python -m pip install -r requirements-openai-optional.txt`를 먼저 실행한다. Notebook의 `RUN_OPTIONAL_LIVE_PROVIDER=True`와 해당 `*_LIVE_OPT_IN=1`을 모두 명시했을 때만 live provider를 호출한다. 준비되지 않았다면 Fixture로 계속한다. Live Candidate는 별도 Golden 평가가 없으면 Release 판단에 사용하지 않고 `LIVE_PROVIDER_CANDIDATE_EVALUATION_REQUIRED/HOLD`로 남긴다.

확인:

```text
provider_requested
provider_used
model
fallback_reason
schema_valid
```

## 5차시 · Hybrid Review

```bash
python -m pytest -q tests/test_day3_review_copilot.py -k "workflow or evidence"
```

1. Static Finding을 확인한다.
2. Focused Test의 실제 Exit Code를 확인한다.
3. Candidate Finding을 확인한다.
4. `learner_grounded_candidates()`를 직접 작성해 실제 Added Line 밖의 후보를 제거한다.
5. 같은 `path + line + rule_id` 중복 Finding이 제거되는지 확인한다.
6. Test를 실행하지 않은 결과가 `READY`가 아닌지 확인한다.

## 6차시 · LangGraph Human Review

1. Start Cell을 실행한다.
2. Interrupt Payload를 읽는다.
3. 유지(`approve`), 수정(`edit`), 제외(`reject`) 중 하나를 선택한다.
4. 같은 `thread_id`로 Resume Cell을 한 번 실행한다.
5. 최종 State와 Audit Log에서 선택한 Decision을 확인한다.
6. 같은 `REVIEW_DECISION`이 8차시 Workflow에 전달되는지 확인한다. `reject`이면 GitHub 단계는 `HOLD`다.

주의:

- 완료된 Thread를 다시 사용하지 않는다.
- 승인 전 PR Comment를 쓰지 않는다.
- 모든 결과에서 `external_write=false`를 확인한다.

## 7차시 · Review Eval

1. 8개 Case의 Golden Finding을 읽는다.
2. `learner_review_metrics()`를 직접 작성해 Precision·Recall·F1을 계산한다.
3. 안전한 Negative Case의 False Positive가 0인지 확인한다.
4. 예상된 Parser Failure가 같은 Error Code로 통과하는지 확인한다.
5. `READY`와 `HOLD` 기준을 기록한다.

## 8차시 · Localhost Service

```bash
python -m labs.day3.review_copilot.web --port 8765
```

표시된 주소를 브라우저에서 연다.

1. Synthetic Case를 선택한다.
2. Review를 실행한다.
3. Finding과 Evidence Line을 확인한다.
4. Finding을 유지·수정·제외한다.
5. JSON과 Markdown을 내려받는다.
6. 자동 Comment·자동 Merge가 없음을 확인한다.

## GitHub PR

완성본이 아닌 검토 단계임을 분명히 하기 위해 첫 PR은 `Draft PR`로 만든다.

```bash
git switch -c codex/day3-<이름>
git status --short
git add <이번 실습 파일만>
git diff --cached
git commit -m "feat(day3): add review rule and boundary test"
git push -u origin HEAD
gh pr create --draft --base main --head codex/day3-<이름>
gh pr checks --watch
```

PR 본문은 `.github/pull_request_template.md`의 안내 항목을 실제 내용으로 채운 별도 파일을 사용한다. Template 원본을 그대로 `--body-file`로 보내지 않는다.

Codex Review가 연결된 저장소:

```text
@codex review
```

PR 결과에서 구분할 것:

| 항목 | 의미 |
|---|---|
| CI | Test와 정적 검사의 결정론 결과 |
| AI Review | 변경 위험에 관한 검토 후보 |
| Human Review | 조직 맥락과 Merge 여부 판단 |

## Codex Task

다음 내용을 Codex에 복사한다.

```text
목표: Review Copilot에 새 Rule 한 개와 허용·차단 Test를 추가해 주세요.

먼저 AGENTS.md, labs/day3/review_copilot/README.md,
labs/day3/review_copilot/CODEX_TASK.md, tests/test_day3_review_copilot.py를 읽어 주세요.

변경 허용 범위:
- labs/day3/review_copilot/
- tests/test_day3_review_copilot.py
- labs/day3/review_copilot/fixtures/cases/

완료 조건:
- Focused Test 통과
- 변경된 줄에만 Finding 생성
- Stable Error Code 유지
- 외부 서비스 변경과 자동 Merge 없음

마지막에 변경 파일, 핵심 Diff, Test 명령과 결과를 보고해 주세요.
```

### 선택 비교 · Codex와 Claude Code

같은 Task를 두 도구에 동시에 시키지 않는다. 먼저 Codex branch의 변경·Test 결과를 보존한 뒤, 독립된 Claude branch에서 같은 요청을 실행한다.

```bash
git switch main
git switch -c codex/day3-rule-본인이니셜
# CODEX_TASK.md의 요청 실행 → Test → Commit

git switch main
git switch -c claude/day3-rule-본인이니셜
# 동일한 요청 실행 → Test → Commit
```

비교 기준은 말투가 아니라 다음 다섯 가지다.

- 허용 경로 준수
- 허용·차단 Test의 실제 통과
- 실제 추가 라인에 근거한 Finding
- 최소 Diff와 이해 가능한 이름
- 외부 서비스 변경·자동 Merge 없음

두 branch의 우열은 AI가 결정하지 않는다. `git diff main...<branch>`와 터미널 Test 결과를 사람이 같이 본다.

## 오류 복구

| 오류 | 확인 | 복구 |
|---|---|---|
| `WORKSPACE_ROOT_NOT_FOUND` | 현재 Folder | Repository Root에서 Notebook 실행 |
| `MODULE_NOT_FOUND` | Kernel Python | `.venv312` 재선택 |
| `EMPTY_DIFF` | Diff 내용 | 제공 Fixture 선택 |
| `DIFF_PATH_BLOCKED` | File Path | Relative Path 사용 |
| `CONTEXT_BUDGET_EXCEEDED` | Byte Limit | 관련 File만 남기기 |
| Provider Opt-in 오류 | 환경 변수 | Fixture로 계속 |
| Graph Resume 오류 | Thread ID | 새 Start 후 같은 ID로 한 번 Resume |
| Port 사용 중 | Localhost Port | 다른 Port 지정 |
| CI 실패 | 첫 실패 Test | Local에서 같은 명령 실행 |
