# 40시간 실습 정의와 차시별 실행 지도

## 결론

이 과정의 중심은 웹사이트 구경이나 생각 나누기가 아니라, 하나의 Agent 서비스를 5일 동안 점진적으로 만드는 소프트웨어 실습이다.

1. 1일차: 안전한 Agent 실행 골격
2. 2일차: 한국어 회의·STT 서비스
3. 3일차: 코드 리뷰 Agent
4. 4일차: GitHub·LangGraph 승인 Workflow
5. 5일차: LangSmith 관측·평가·배포 운영

현재 저장소에는 1~5일차 Notebook과 실행 완료본, 핵심 Python 모듈, 합성 데이터, 자동 test, 브라우저 Demo가 있다. 다만 준비 수준은 차시마다 다르다. 1일차 4~8차시는 수강생이 그대로 따라갈 수 있는 수준이고, 2~5일차는 하루의 중심 Notebook과 Python/test는 준비되어 있으나 8개 차시를 각각 안내하는 Notebook 셀이 아직 충분히 분리되지 않은 구간이 있다. 이 문서에서 그 상태를 `A·B·C`로 구분한다.

## 실습의 정의

### 소프트웨어 실습

다음 다섯 조건을 모두 포함하는 활동만 `소프트웨어 실습`으로 부른다.

1. 수강생이 VS Code, Jupyter Notebook 또는 Terminal을 직접 조작한다.
2. 코드·설정·Prompt·Schema·test 중 하나를 직접 작성하거나 수정한다.
3. 실행 명령으로 정상 경로와 대표 실패 경로를 확인한다.
4. JSON·trace·test 결과·diff·build 결과처럼 다시 확인할 수 있는 완료 증거가 남는다.
5. 외부 게시·메일·PR comment·trace upload·배포에는 사람 승인 단계가 있다.

공식 문서나 서비스 홈페이지를 여는 일은 개념의 근거를 확인하는 `자료 확인`이다. 문제를 고르고 입력·결과·금지 행동을 적는 일은 `Ideation`, 상태와 권한을 설계하는 일은 `설계 워크숍`이다. 이 활동들을 소프트웨어 실습이라고 부르지 않는다.

### 한 차시의 기본 리듬

| 구간 | 기본 시간 | 진행 내용 |
|---|---:|---|
| 개념 강의 | 10~12분 | 처음 나오는 용어·문제·선택 이유 |
| 강사 시연 | 8~10분 | 입력·명령·정상 결과·대표 실패를 먼저 실행 |
| 소프트웨어 실습 | 20~25분 | 같은 코드를 직접 실행하고 한 가지를 수정 |
| 실행 확인 | 5분 | 완료 증거와 첫 오류 한 줄 확인 |

강사가 먼저 완성 경로를 보여주고 수강생이 같은 저장소·파일·명령을 따라간다. 빠른 수강생은 boundary test나 Codex 개선 작업으로 확장하고, 막힌 수강생은 deterministic fixture로 같은 계약과 Workflow를 계속 확인한다.

### 완료 판정

| 확인 항목 | 통과 기준 |
|---|---|
| 입력 | 합성·공개·비식별 데이터이며 workspace 안에 존재 |
| 실행 | 복사 가능한 명령 또는 실행 가능한 Notebook 셀 존재 |
| 정상 경로 | 기대 status·schema·파일이 실제로 생성 |
| 실패 경로 | raw traceback 대신 stable error code 또는 HOLD 반환 |
| test | 정상 case와 가장 중요한 경계 case 통과 |
| 사람 판단 | approve·edit·reject 또는 READY·HOLD가 기록 |
| 보안 | `.env`, token, 실제 고객·회의 데이터가 결과물에 없음 |

## 준비 상태 기준

| 상태 | 의미 |
|---|---|
| A · 바로 진행 | 수강생용 Notebook/명령, 코드, 정상·실패 결과, test가 연결됨 |
| B · 보강 필요 | 코드와 test는 있으나 해당 차시 전용 Notebook 셀·설명이 부족함 |
| C · 선택 실행 | 계정·token·네트워크·외부 쓰기가 필요해 강사 승인 후 별도 실행 |

## 4일차 · GitHub·LangGraph 승인 Workflow

중심 결과는 `PR 읽기 → 리뷰 생성 → 사람 승인 → dry-run → 선택 게시`다. 외부 쓰기는 기본값이 아니며, 수업 저장소에는 fake publisher를 사용한다.

| 차시 | 구분 | 직접 확인·제작할 것 | 주 파일·명령 | 완료 증거 | 상태 |
|---|---|---|---|---|---|
| 1차시 | Fixture 실습 | repo·PR number·head SHA가 있는 synthetic target 검증 | `day4_service_lab.ipynb`, `data/day4_github/pr_fixture.json` | `pr_target.json`, 누락 field 오류 | A |
| 2차시 | 인증·환경 실습 | `.env` ignore, `.env.sample`, 최소 권한, 401 즉시 중단 | `git check-ignore -v .env`, `.env.sample` | secret 미추적 확인 | B |
| 3차시 | API adapter 실습 | 200·401·403·404·422·429를 서로 다른 복구 계약으로 처리 | `src/course_services/github_service.py`, service test | `github_read_result.json`, status별 error code | B |
| 4차시 | LangGraph 실습 | validate→load diff→review→human review→dry-run node와 분기 | `src/langgraph_lab.py`, `python -m src.langgraph_lab --decision all` | approve·edit·reject terminal state | B |
| 5차시 | Idempotency 실습 | 같은 target·SHA·body를 두 번 실행해 publisher 1회 보장 | `day4_service_lab.ipynb`, `pytest -k idempotent` | `checkpoint_and_audit.json`, `reused=true` | A |
| 6차시 | Human Approval 실습 | interrupt payload에서 대상·근거·초안을 보고 승인·수정·거절 | `src/langgraph_lab.py`, `web-demo/app.js` | `review_decision.json`, reject 시 external write 없음 | B |
| 7차시 | Dry-run 실습 | 실제 API와 같은 comment body·target·hash key를 local JSON으로 생성 | `day4_service_lab.ipynb`, `pytest -k dry_run` | `review_comment_plan.json` | A |
| 8차시 | 선택 게시 실습 | 본인 sandbox repo 한 건에만 승인된 comment 게시, remote ID 기록 | 강사 승인 후 별도 live adapter | `day4_audit_record.json`, rollback 경로 | C |

4일차의 안전 중심은 잘 잡혀 있다. fake publisher·dry-run·중복 방지는 바로 실행 가능하다. 실제 GitHub write adapter가 기본 코드에 없는 것은 누락이 아니라 안전 정책이다. 수업에서 live 게시를 하려면 본인 sandbox repo, 최소 scope token, 사전 승인, 한 건 제한, rollback을 별도 런북으로 고정해야 한다.
