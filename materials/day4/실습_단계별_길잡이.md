# 4주차 실습 단계별 길잡이

[실습 Notebook](day4_pr_document_automation.ipynb)을 옆에 열고 사용합니다. 이 문서는 명령을 실행할 위치, 직접 바꿀 부분, 실행 결과를 확인하는 방법을 연결합니다.

## 처음 시작하는 순서

1. Git으로 받은 저장소 또는 ZIP을 푼 **폴더 전체**를 VS Code로 엽니다. Notebook만 다른 폴더로 옮기지 않습니다.
2. 프로젝트 최상위에 `requirements-day4.txt`와 `labs` 폴더가 있는지 확인합니다.
3. [설치 가이드](2026_Day4_수강생_실습가이드.md)의 Mac 또는 Windows 명령으로 설치합니다. 기존 가상환경이 있으면 같은 환경을 사용합니다.
4. `materials/day4/day4_pr_document_automation.ipynb`를 열고 오른쪽 위 Kernel에서 설치에 사용한 Python을 선택합니다.
5. 첫 코드 셀부터 순서대로 실행합니다. 화면에 나온 `결과 폴더` 경로를 메모합니다. 오늘 수정한 결과를 찾을 기준입니다.

### 헷갈리기 쉬운 세 위치

| 이름 | 실제 위치 | 용도 |
|---|---|---|
| 저장소 루트 | `requirements-day4.txt`가 있는 폴더 | 설치·모듈 실행 명령의 기준 |
| Notebook 폴더 | `materials/day4/` | 셀과 설명이 들어 있는 위치 |
| 이번 결과 폴더 `RUN` | `output/day4-notebook-runs/날짜_실행ID/` | 이번 실행의 결과 파일 |

`ROOT`, `RUN`, `EXERCISE`는 Notebook이 정한 변수입니다. Notebook에 나온 짧은 코드 조각을 새 터미널에 바로 붙이면 이 변수를 찾지 못할 수 있습니다. 슬라이드의 **Notebook 코드**는 앞선 설치·준비 셀을 실행한 Notebook에서 사용합니다. **터미널 명령**은 저장소 루트에서 실행합니다.

장표에만 있는 추가 코드는 해당 차시에 새 코드 셀을 넣어 실행합니다. 앞의 데이터 준비 셀을 다시 실행하면 수정한 변수가 초기화될 수 있습니다. Word는 정상 `my_rewrites`를 유지한 채 저장 셀을 실행합니다. 7차시 `walkthrough.json` 저장 코드는 기존 JSON 저장 셀 아래에 넣고, 이후에는 Node 준비 → PPT 생성 → 구조 검사만 실행합니다. 기존 JSON 저장 셀을 재실행하면 `brief_path`가 다시 바뀝니다.

`NameError`가 나오면 해당 변수를 만드는 위쪽 셀부터 실행합니다. Kernel을 재시작하면 메모리의 변수가 사라집니다. 첫 셀을 다시 실행하면 새 `RUN` 폴더가 생기므로, 이전에 수정한 파일과 새 파일을 혼동하지 않습니다.

## 차시별 작업 지도

아래 출력 경로는 모두 **이번 `RUN` 폴더 기준**입니다.

| 차시 | Notebook에서 찾을 제목 | 직접 작업 | 결과 위치 |
|---|---|---|---|
| 1 | 대상 PR과 변경 코드 | 대상 확인 함수·오류 입력·실습 폴더 확인 | `pr/my-exercise/` |
| 2 | 리뷰 초안과 코드 수정 | 결제 코드 수정·테스트·리뷰 내용 확인 | `pr/my-exercise/checkout.py`<br>`pr/report/review.html` |
| 3 | 테스트와 CI | 테스트 추가·CI 파일 작성·승인 후 변경 검사 | `pr/my-exercise/test_checkout.py`<br>`pr/day4-checkout-tests.yml` |
| 4 | WBS와 Gantt Chart | 진척률·날짜 변경·Excel 생성 | `excel/WBS_my_project.xlsx` |
| 5 | 객관식 채점과 조건부서식 | 답안 오류 복구·정답 변경 비교 | `excel/Exam_my_class.xlsx`<br>`excel/Exam_changed_key.xlsx` |
| 6 | Word 이력서 개선 | 경력 문장 변경·수치 검사·DOCX 생성 | 셀에 출력된 개선 전후 DOCX 링크 |
| 7 | 데이터 기반 PPT 생성 | 같은 업무 데이터로 입력과 PPT 재생성 | 셀에 출력된 `ppt/project_brief.json`·PPT 링크 |
| 8 | 결과 연결과 미니 프로젝트 준비 | 생성 파일 열기·다음 기능과 테스트 정의 | `index.html`·프로젝트 요청서 |

## 1차시: 검토할 코드와 내 작업 폴더

1. `load_fixture()` 결과에서 `repo`, `number`, `head_sha`를 찾습니다. 예제 저장소 이름은 실제 게시 대상이 아닙니다.
2. `my_target_matches` 함수의 두 조건을 읽습니다. 같은 저장소인지, 같은 PR 번호인지 확인하는 코드입니다.
3. 틀린 저장소·잘못된 SHA를 넣는 셀을 실행합니다. `예상한 차단`은 실패한 수업이 아니라 잘못된 작업을 멈춘 결과입니다.
4. `내 실습 폴더` 셀을 실행하고 출력된 `checkout.py` 경로를 VS Code에서 엽니다.
5. `baseline_test` 결과를 봅니다. 처음에는 **4 failed, 1 passed**가 맞습니다. 수정할 결함을 일부러 넣었습니다.

`EXERCISE_EXISTS`가 나오면 준비 셀을 반복해 기존 폴더를 덮으려 했는지 확인합니다. 이미 만들어 둔 `EXERCISE`를 사용해 다음 셀로 진행합니다. 새 실습을 시작하려면 첫 셀부터 실행해 새로운 `RUN`을 사용합니다.

## 2차시: 결제 코드 수정과 재검사

1. `EXERCISE / 'checkout.py'`를 엽니다. `labs/.../fixtures/checkout.py`는 수업 원본이므로 직접 고치지 않습니다.
2. 가격·수량·쿠폰의 잘못된 입력을 `ValueError`로 거절하도록 수정합니다.
3. 초과 쿠폰 때문에 최종 금액이 음수가 되지 않도록 계산식을 수정하고 저장합니다.
4. `current_test = check_exercise(ROOT, EXERCISE)` 셀을 다시 실행합니다. 기대 결과는 **5 passed**입니다.
5. 정상 쿠폰 계산도 그대로 맞는지 봅니다. 테스트 기대값을 바꿔 초록색으로 만드는 것은 코드 수정과 다릅니다.
6. 리뷰 파일 생성 셀을 다시 실행하고 `review.html`을 엽니다. 화면의 테스트 결과가 방금 수정한 코드의 결과인지 확인합니다.

실제 Codex 리뷰는 선택입니다. `RUN_CODEX_LIVE=False` 상태에서는 계정을 호출하지 않습니다. True로 바꿀 때에는 CLI 로그인·사용량·공개 예시 입력을 먼저 확인합니다. 호출에 실패했는데 fixture를 실제 AI 응답으로 설명하지 않습니다.

수정했는데 결과가 같다면 **파일 저장 여부**, **현재 EXERCISE 경로**, **재실행한 셀**을 순서대로 확인합니다. 생성된 파일만 새로 열고 테스트 셀을 실행하지 않았다면 이전 결과가 보일 수 있습니다.

## 3차시: 내가 쓴 테스트와 CI

1. `test_checkout.py`에서 정상 입력 한 건과 초과 쿠폰 한 건을 찾습니다.
2. 쿠폰이 정확히 총액과 같은 입력을 추가합니다. 어떤 결과를 기대하는지 코드 전에 한 줄로 적습니다.
3. 추가한 테스트만 실행한 뒤 전체 테스트를 다시 실행합니다. 테스트 함수 이름이 `test_`로 시작하는지 확인합니다.
4. Notebook이 만든 `day4-checkout-tests.yml`을 엽니다. trigger, 권한, Python 설치, pytest 경로를 찾습니다.
5. 개인 저장소에 적용하는 경우 **실제 코드 위치와 YAML의 경로를 맞춘 뒤** `.github/workflows/`에 배치합니다. 수업 공유 저장소에는 올리지 않습니다.
6. 오래된 SHA와 중복 리뷰를 넣는 셀을 실행합니다. 같은 PR이라도 코드 버전이 달라지면 이전 승인을 다시 사용할 수 없습니다.

`pr/reference-only/`는 참고 구현을 확인하는 별도 폴더입니다. 그곳의 `5 passed`는 내가 수정한 `pr/my-exercise/`의 통과를 뜻하지 않습니다. 개인 GitHub의 Checks 확인까지 수행하지 않았다면 로컬 테스트 결과와 구분해 기록합니다.

## 4차시: 입력을 바꾸면 움직이는 WBS

1. `tasks_my`는 원본을 복사한 데이터입니다. `id == 'W04'`인 업무를 찾습니다.
2. `progress`를 `0.8`에서 `1.0`으로 바꾸고 상태 계산 셀을 실행합니다. W04의 상태와 전체 완료·지연 개수를 비교합니다.
3. 파일 생성 셀을 실행하고 `WBS_my_project.xlsx`를 엽니다. 동일한 파일명을 다시 쓰려 하면 새 이름을 사용합니다.
4. WBS 시트에서 **F12 진척률**, **I12 상태**를 비교합니다. 기본 비교 기준일은 **B4**입니다.
5. 다른 복사본에서 D:E의 날짜를 바꾸고 L:AM 간트 영역의 변화를 확인합니다. 날짜처럼 보이는 문자열과 실제 날짜 셀을 구분합니다.
6. 잘못된 종료일 또는 선행 일정 충돌을 넣어 확인한 뒤 원래 값으로 복구합니다. 오류 메시지를 빈칸으로 덮지 않습니다.

Python 계산은 바뀌었는데 Excel 화면이 그대로라면 열린 파일 이름과 기준일을 먼저 봅니다. `openpyxl`은 수식을 저장하는 도구이며 수식 계산 엔진이 아닙니다. Excel 또는 LibreOffice에서 열어 재계산하고 저장합니다. 샘플은 공휴일을 반영하지 않습니다.

## 5차시: 채점 오류와 정답 변경의 구분

1. 원본 합성 데이터에서 **정답표**와 **응답 목록**을 구분합니다. 본인의 실제 학생 성적은 넣지 않습니다.
2. 오류 복구 실험은 합성 답안의 `9`를 유효한 보기로 바꿉니다. 실제 시험에서는 원본 답안 근거 없이 값을 수정하면 안 됩니다.
3. `Exam_my_class.xlsx`를 열어 **L35**와 **AT35**를 비교합니다. 합성 오류 복구 후 집계 대상은 26명에서 27명으로 바뀝니다.
4. 정답표 변경 실험은 별도 복사본 `key_changed`를 사용합니다. 첫 문항 정답을 1에서 2로 바꿉니다.
5. `Exam_changed_key.xlsx`의 **D8**이 2인지 확인합니다. `Exam_my_class.xlsx`와 총점·순위·문항 정답률을 비교합니다.
6. 빈 답안, 결시, 보기 범위를 벗어난 값이 서로 어떻게 처리되는지 확인합니다. 정답 색만 보고 채점 완료로 판단하지 않습니다.

Google Sheets로 이어가려면 합성 XLSX를 **본인 Drive에 새 파일로 업로드**해 사용합니다. 변환 또는 Apps Script 설치는 선택 확장입니다. 자세한 방법은 [Google Sheets 안내](../../labs/day4/office_lab/google_sheets/README.md)를 따릅니다. 원본 성적표를 변경하는 과정은 아닙니다.

## 6차시: 경력 사실과 Word 문장의 비교

1. `career_facts.json`에서 개선할 사실의 `id`를 고릅니다. 이 값이 근거를 연결하는 Fact ID입니다. 원문의 숫자와 Role을 먼저 읽습니다.
2. Notebook의 `my_rewrites`에서 한 문장을 짧고 자연스럽게 바꿉니다. 먼저 한 문장만 작업합니다.
3. `audit_rewrite`로 새 숫자·잘못된 ID 검사를 실행합니다.
4. `REQUIRES_HUMAN_REVIEW`는 자동 검사가 끝났지만 의미 확인이 남았다는 뜻입니다. ‘참여’를 ‘총괄’로 바꾸는 과장은 숫자가 같아도 확인해야 합니다.
5. DOCX 생성 셀을 실행하고 개선 전·후 파일을 모두 엽니다. 바꾼 문장이 실제 결과에 들어갔는지 봅니다.
6. 제목·본문의 글꼴과 문단 간격을 한 항목만 바꿔 다시 생성합니다. 전체 페이지의 잘림을 확인합니다.

원본 연락처, 고객명, 실제 평가 정보는 연습 자료에 넣지 않습니다. Word 파일을 직접 편집한 내용과 코드에서 수정한 내용은 별도입니다. 코드로 다시 생성할 파일이라면 변경 사항을 입력 데이터 또는 생성 코드에도 반영해야 합니다.

## 7차시: 동일 데이터의 PPT 보고서

1. Node 준비 셀을 실행합니다. `node` 또는 라이브러리가 없으면 제공 안내의 설치를 마칩니다.
2. 4차시에서 수정한 `tasks_my`와 같은 기준일로 보고서 데이터를 만듭니다.
3. `ppt/project_brief.json`에 들어간 전체·완료·지연 수치를 확인한 뒤 PPT 생성 셀을 실행합니다. 장표 추가 경로는 `walkthrough.json`이므로 현재 `brief_path` 값을 확인합니다.
4. 생성한 PPT에서 편집 가능한 표의 셀을 클릭합니다. Excel과 PPT의 수치가 같은 기준일을 쓰는지 비교합니다.
5. 업무명을 길게 바꾸어 넘침을 확인합니다. 내용을 삭제하기 전에 줄바꿈·열 너비·행 높이를 검토하고, 임의로 글씨를 작게 줄이지 않습니다.
6. PDF로 내보내거나 인쇄 저장해 모든 페이지를 확인합니다. 문제를 수정한 뒤 PPT와 PDF를 함께 다시 만듭니다.

PPT 파일이 이미 열려 있어 저장이 막히면 닫은 뒤 새 이름으로 다시 생성합니다. 생성 단계를 건너뛴 안내가 나왔다면 배포용 예제를 열어 보는 것과 직접 생성 성공을 구분합니다.

## 8차시: 결과 전달과 프로젝트 선택

1. 마지막 셀의 `index.html`에서 이번 실행의 결과 파일을 차례로 엽니다. 파일의 존재와 내용의 정확성은 별도로 확인합니다.
2. [업무자동화 프로젝트 선택 가이드](../day5/업무자동화_프로젝트_선택가이드.md)에서 본인의 반복 업무와 가까운 사례를 고릅니다. 목록에 없는 업무를 직접 제안해도 됩니다.
3. 사용자 한 명, 입력 파일 한 종류, 결과 한 종류부터 정합니다. Gmail·Slack 등 외부 연결은 먼저 로컬 샘플로 대체할 수 있는지 검토합니다.
4. Notebook이 만든 프로젝트 요청서에 정상 입력과 실패 입력을 씁니다. 주제 선택·자료 수집은 Ideation이며 구현 완료로 표시하지 않습니다.
5. Codex에 **첫 기능과 그 테스트**를 요청합니다. 생성된 코드를 읽고 실제 실행한 뒤 수정 전후를 비교합니다.
6. 다른 사람이 README의 명령으로 다시 실행할 수 있는지 확인합니다. 게시·발송·원본 덮어쓰기는 사람 확인 이후의 별도 단계입니다.

36개 사례는 선택 예시입니다. 모든 프로젝트의 완성 코드가 제공되는 것은 아닙니다. 가이드에서 ‘기존 코드 재사용’과 ‘새 구현 필요’를 확인하고, 다음 주 150분 제작 범위를 정합니다.
