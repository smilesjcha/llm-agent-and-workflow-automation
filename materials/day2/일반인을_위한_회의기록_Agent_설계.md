# 일반인을 위한 회의기록 Agent 설계

## 한 문장 정의

`Well-being 회의기록 Agent`는 여러 형태의 회의 자료를 하나의 구조로 정리한 다음, 회의의 목적과 기존 맥락을 고려해 요약·구성원별 관점·할 일·단기/중기/장기 인사이트를 초안하고, 원문 근거와 사람의 승인을 거쳐 문서와 이메일 초안으로 남기는 로컬 우선 소프트웨어다.

핵심은 “요약을 잘하는 AI”보다 “잘못된 요약이 자동 발송되지 않는 서비스”에 있다.

---

## 1. 먼저 구분할 세 가지

### LLM

LLM은 글을 읽고 글을 만드는 확률적 엔진이다. 회의 요약, 의견 분류, 표현 다듬기에 적합하지만 파일 저장, 권한 확인, 이메일 발송을 스스로 안전하게 보장하지는 않는다.

```text
텍스트 + 요청 + 맥락 → LLM → 텍스트 또는 구조화 JSON
```

### 고정 Workflow

고정 Workflow는 순서를 사람이 미리 정한 소프트웨어다. 항상 `입력 확인 → 정규화 → 요약 → 검증 → 승인 → 저장`을 거친다면 Workflow로 만드는 편이 싸고 안정적이다.

### Agent

Agent는 목표·현재 상태·정책을 보고 “어떤 정보가 더 필요한지”, “허용된 도구 중 무엇을 쓸지”, “언제 멈추고 사람에게 물을지”를 한정된 범위에서 판단한다.

| 구분 | 사람에게 보이는 예 | 코드의 본질 | 이 서비스의 적용 |
|---|---|---|---|
| LLM | “이 회의를 요약해 줘” | 하나의 모델 호출 | 요약·관점·인사이트 초안 |
| Workflow | 업로드하면 정해진 단계 실행 | 미리 정한 node와 분기 | 전사·검증·승인·초안 저장 |
| Agent | 요청에 따라 최근 Notion과 Slack만 조회 | 정책 안의 도구 선택·중단 | 입력 유형, 검색 필요성, 출력 경로 판단 |

### 이 과정의 설계 원칙

회의 전사·요약·근거 검증·승인은 고정 Workflow로 둔다. Agent는 상황별 입력 adapter, 추가 자료 검색 필요성, 허용된 도구 선택에만 제한적으로 쓴다. 모든 단계를 Agent에게 넘기면 비용과 실패 경로만 늘어난다.

## 2. 사용자가 보는 서비스

### 입력 세 가지

| 상황 | 사용자가 가진 것 | 서비스가 먼저 할 일 | STT |
|---|---|---|---|
| Google Meet | 전사 텍스트, 참석자/화자 정보 | 화자·시각·발화 분리, 참석자 이력 결합 | 불필요 |
| ClovaNote | 내보낸 TXT | 파일 인코딩·화자 형식·timestamp 확인 | 불필요 |
| 녹음 파일 | WAV·MP3·M4A·OGG·WEBM | 동의·파일·코덱 확인 후 local STT | 필요 |

텍스트가 있는데 다시 STT를 돌리지 않는다. 이 한 줄이 처리 시간과 비용을 가장 크게 줄인다.

### 공통 출력

1. 회의 목적과 배경
2. 기존 맥락과 이번 회의의 변화
3. 핵심 요약과 결정 사항
4. 구성원별 발언·우려·제안
5. 담당자·기한·근거가 있는 To-do
6. 단기·중기·장기 인사이트
7. 번아웃·업무 편중·미합의를 보는 well-being 점검
8. 각 결론이 나온 원문 발화 ID
9. Markdown 문서와 내부/외부 이메일 초안

“구성원의 생각”은 그 사람의 내면을 추측하는 것이 아니다. 실제 발언에서 확인된 관점·우려·제안만 정리한다. 발언이 없으면 `확인할 수 없음`으로 남긴다.

## 3. 전체 아키텍처

```text
[입력]
  ├─ Google Meet 전사 + 참석자 정보
  ├─ ClovaNote TXT
  └─ 녹음 파일
          │
          ▼
[입력 Adapter]
  형식 확인 · 파싱 · 필요한 경우만 STT
          │
          ▼
[TranscriptEnvelope 공통 계약]
  meeting_id · source · participants · segment_id · speaker · time · text
          │
          ├─ [DomainContext]
          │    산업 · 목적 · 용어 · 기존 결정 · 제약 · 톤
          │
          └─ [Retrieval Policy]
               필요한 경우만 · read-only · 출처 · 최근 범위 · 민감정보 제외
          │
          ▼
[고정 분석 Workflow]
  목적/맥락 → 요약 → 참석자 관점 → To-do → 인사이트
          │
          ▼
[근거·Schema 검증]
  없는 segment ID · 없는 담당자 · 임의 기한 · 누락 필드 → HOLD
          │
          ▼
[사람 승인]
  승인 · 수정 · 거절
          │
          ▼
[출력 Adapter]
  local MD · 이메일 초안 · Notion/Confluence 게시 계획
  ※ 외부 저장·발송은 두 번째 명시적 승인 전까지 금지
```

이 구조에서 LLM은 중앙의 “생각” 일부를 담당한다. 파일을 읽는 것, 형식을 검사하는 것, 권한을 막는 것, 근거 ID를 대조하는 것은 일반 소프트웨어가 담당한다.

## 4. TranscriptEnvelope 공통 계약

세 가지 입력을 서비스 안쪽에서 동일하게 취급하려면 공통 형식이 필요하다. 이를 `TranscriptEnvelope`이라 부른다.

```json
{
  "meeting_id": "meeting-2026-08-30-product-weekly",
  "source_type": "google_meet_text",
  "source_name": "product_weekly.txt",
  "language": "ko",
  "consent_confirmed": true,
  "participants": [
    {"id": "p01", "display_name": "김PM", "role": "상품 PM"},
    {"id": "p02", "display_name": "이개발", "role": "Backend Engineer"}
  ],
  "segments": [
    {
      "id": "s001",
      "speaker_id": "p01",
      "start_seconds": 12.4,
      "end_seconds": 21.8,
      "text": "오늘은 탐색 결과 응답 시간을 먼저 확인하겠습니다.",
      "confidence": null,
      "source_ref": "product_weekly.txt#L14"
    }
  ]
}
```

### 필수 규칙

- 하나의 입력은 하나의 `source_type`만 가진다.
- 모든 발화에 변하지 않는 `segment_id`를 붙인다.
- 시각이 없는 TXT는 시각을 만들지 않고 `null`로 둔다.
- 화자를 모르면 임의로 실명을 배정하지 않고 `unknown_01`로 둔다.
- 원본 파일, 전사 텍스트, 최종 요약을 서로 덮어쓰지 않는다.
- 업로드한 음성의 live STT가 실패하면 다른 fixture 전사를 그 음성의 결과처럼 보여 주지 않는다.

### 입력별 정규화

#### Google Meet 전사

1. 텍스트와 참석자 정보를 함께 받는다.
2. 화자명을 참석자 ID에 대응한다.
3. 회의 전·후 chat이 있다면 회의 발화와 다른 자료로 표시한다.
4. 자동 요약이 포함되어도 원문 전사와 섞지 않는다.

#### ClovaNote TXT

1. UTF-8 인코딩을 확인하고, 아니면 사용자에게 수정을 요청한다.
2. 화자/시각/발화 패턴을 파싱한다.
3. 화자 표시가 없으면 화자 분리가 불가능함을 결과에 남긴다.
4. TXT의 요약문과 원문 구간을 구분한다.

#### 녹음 파일

1. 녹음 동의와 처리 권한을 먼저 확인한다.
2. 파일 크기·재생 길이·코덱·손상 여부를 검사한다.
3. local `faster-whisper`로 전사한다.
4. 무음·반복·언어·confidence 기반 품질 Gate를 통과한다.
5. 화자 분리가 없는 STT 결과에 실명을 임의로 붙이지 않는다.

## 5. DomainContext 입력란

LLM이 산업 용어를 모른다고 가정하고 설명한다. 비밀 정보를 무제한으로 넣는 공간이 아니라, 이번 회의를 정확히 이해하는 데 필요한 최소 정보만 넣는다.

| 항목 | 일반인이 입력할 질문 | 예시 |
|---|---|---|
| 산업/업무 | 어떤 일을 하는 회의인가 | 이커머스 상품 탐색 |
| 회의 목적 | 오늘 어떤 결정을 하려고 했나 | 응답 지연 원인과 배포 여부 |
| 기존 맥락 | 회의 전에 이미 알고 있던 것은 | 지난주 p95 3.2초 |
| 용어집 | 틀리기 쉬운 약어는 | PDP=상품상세, SRP=검색결과 |
| 제약 | 바꾸면 안 되는 기준은 | 결제 정보는 출력에서 제외 |
| 관점 | 누구를 위한 문서인가 | PM·개발·CS 공통 |
| 톤 | 어떤 문체로 쓸까 | 간결한 업무체, 과장 금지 |
| 민감도 | 외부 모델에 보내면 안 되는 것은 | 실명·고객 ID·매출액 제외 |

### 복사해 쓰는 Context 양식

```yaml
domain: "이커머스 / 상품 탐색"
meeting_goal: "응답 지연 원인과 이번 주 배포 범위 합의"
prior_context:
  - "지난주 p95 3.2초"
  - "캐시 적용 후 정확도 회귀 검증 필요"
glossary:
  PDP: "상품상세"
  SRP: "검색결과"
constraints:
  - "회의에 없는 담당자나 기한을 만들지 않음"
  - "고객 실명을 출력하지 않음"
audience: ["PM", "Backend", "Data"]
tone: "간결한 업무체"
```

## 6. 기존 맥락 Retrieval과 MCP 정책

### 먼저 물을 일곱 가지

1. 이번 요청에 정말 외부 자료가 필요한가?
2. 어떤 서비스를 읽어야 하는가?
3. 어느 공간·프로젝트·채널만 허용할까?
4. 며칠간의 자료만 볼까?
5. 검색어와 최대 결과 수는 얼마인가?
6. 실명·고객정보·기밀을 마스킹했는가?
7. 가져온 문장의 출처를 남길 수 있는가?

### 최소 권한 계약

| 정책 | 기본값 | 예외 요청 시 |
|---|---|---|
| 필요성 | 회의 원문만으로 부족할 때만 | 왜 필요한지 먼저 설명 |
| 권한 | read-only | write 필요 시 따로 승인 |
| 기간 | 최근 14일 | 기간 확장 이유와 영향 표시 |
| 범위 | 지정 공간·페이지·채널 | 전사 검색 금지 |
| 결과 수 | 소스별 최대 5개 | 사람이 추가 검색 승인 |
| 민감정보 | 제외·마스킹 | 사내 보안 정책 우선 |
| 출처 | URL/문서 ID/시각 필수 | 출처 없음은 근거로 미사용 |
| 외부 쓰기 | 금지 | 미리보기 후 2차 승인 |

### MCP를 쓰는 순서

```text
요청 해석
  → 외부 맥락 필요성 판단
  → 읽을 소스·범위·기간 제안
  → 사람의 조회 승인
  → read-only MCP 조회
  → 출처와 함께 맥락 정리
  → 요약 Workflow에 주입
```

MCP는 “AI가 알아서 사내 정보를 다 찾는 기능”이 아니다. 허용된 서비스의 허용된 함수를 호출하는 연결 방식이다. 접속되었다는 사실은 전체 조회 권한이나 자동 게시 승인을 의미하지 않는다.

## 7. 분석 결과 계약

```json
{
  "meeting_purpose": "탐색 API 응답 지연 원인과 배포 범위 합의",
  "prior_context": ["2026-08-23 p95 3.2초"],
  "summary": "캐시 미적용 구간을 우선 수정하고 정확도 회귀 검증 후 배포하기로 함.",
  "participant_views": [
    {
      "participant_id": "p02",
      "observed_view": "캐시 키 설계를 먼저 바꾸자고 제안",
      "evidence_ids": ["s014", "s018"]
    }
  ],
  "action_items": [
    {
      "task": "캐시 키 패치 PR 작성",
      "owner": "이개발",
      "due_date": null,
      "evidence_ids": ["s031"]
    }
  ],
  "insights": {
    "short_term": ["패치 후 p95와 정확도 동시 확인"],
    "mid_term": ["탐색 query 유형별 캐시 정책 분리"],
    "long_term": ["성능·정확도 통합 release gate 구축"]
  },
  "wellbeing": {
    "confirmed_risks": ["한 담당자에게 장애 분석과 배포가 모두 배정됨"],
    "needs_confirmation": ["배포 담당 분리 가능 여부"],
    "evidence_ids": ["s027", "s031"]
  }
}
```

### 절대 만들지 않는 것

- 원문에 없는 합의
- 언급되지 않은 담당자와 기한
- 발화로 확인할 수 없는 감정·의도·인성
- 의료·법률·인사 진단
- 출처가 없는 기존 맥락

## 8. 근거 검증과 사람 승인

### 기계가 먼저 검사할 것

- 모든 결정·To-do·구성원 관점에 `evidence_ids`가 있는가?
- 그 ID가 실제 `TranscriptEnvelope.segments`에 존재하는가?
- 담당자는 참석자이거나 회의에서 명시된 사람인가?
- 기한은 원문에 있는가? 없으면 `null`인가?
- 출력 Schema의 필수 항목이 다 있는가?
- 민감정보 정책을 위반하지 않았는가?

### 사람이 확인할 것

| 판단 | 의미 | 다음 단계 |
|---|---|---|
| 승인 | 원문과 대조했고 업무에 쓸 수 있음 | local MD·draft 생성 |
| 수정 | 요약·담당자·기한을 사람이 고침 | 수정본 재검증 |
| 거절 | 원문 오류·민감성·정확도 미달 | `HOLD`로 종료 |

`READY`는 “자동으로 발송해도 된다”가 아니라 “사람이 검토할 준비가 됐다”는 뜻이다.

### 외부 쓰기는 두 번째 승인

```text
1차 승인: 회의록 내용이 맞는가?
  → local Markdown·이메일 초안 생성

2차 승인: 어디에, 누구에게, 어떤 내용을 쓸 것인가?
  → Notion/Confluence 게시 또는 이메일 발송
```

수업 버전은 2차 승인 이후의 실제 게시·발송도 수행하지 않는다. 대신 `integration_plan`을 만들어 대상·제목·본문·필요 권한을 미리보기한다.

## 9. 실행 방식 선택

### 선택표

| 방식 | 적합한 사람 | 장점 | 제약 |
|---|---|---|---|
| ChatGPT/Claude 대화 | 코드 없이 한 번 정리 | 시작이 빠름 | 반복 재현·검증·외부 쓰기 통제가 약함 |
| Codex/Claude Code | 코드와 테스트를 함께 만들 사람 | 저장소 점검·수정·테스트 | 작업 범위·권한을 명시해야 함 |
| Jupyter Notebook | 각 단계를 배우고 결과를 남길 사람 | 코드·결과·설명이 한 곳에 있음 | 사용자 제품처럼 쓰기는 불편 |
| local Desktop App | 일반 사용자에게 선물할 사람 | 업로드·입력·미리보기가 쉬움 | Docker/패키지 준비가 필요 |
| OpenAI API | 반복 실행과 서비스 통합 | 구조화 출력·도구 호출·관찰 가능 | 비용·키·데이터 정책 필요 |
| Ollama | 무료·로컬 우선 | 텍스트가 PC 밖으로 나가지 않음 | 설치·메모리·속도·품질 편차 |

### 권장 구성

- 설계·코드 리뷰: 가용한 상위 Codex 또는 Claude Code 모델
- 수업 기본 실행: deterministic fixture
- 무료 live LLM: Ollama `qwen3:4b`
- 선택 API: 계정에 `gpt-5.6-luna`가 실제로 허용된 경우만 opt-in
- 로컬 STT: `faster-whisper`

모델명은 요청한 다음 실제 응답의 `model`/`provider_used`로 확인한다. 접근이 안 되면 다른 모델을 같은 결과처럼 숨기지 않고 `fallback_reason`을 남긴다.

OpenAI의 공식 문서에서 `gpt-5.6-sol`은 복잡한 전문 작업용, `gpt-5.6-luna`는 비용 민감한 고반복 작업용으로 안내된다. API의 reasoning effort와 Codex 앱에 노출되는 설정명은 같지 않을 수 있으므로, 수업에서는 실제 화면과 응답을 기준으로 한다. [GPT-5.6 Sol](https://developers.openai.com/api/docs/models/gpt-5.6-sol), [Responses API](https://developers.openai.com/api/reference/cli/resources/responses/methods/create)

## 10. 비용을 줄이는 설계

Agent가 비싼 이유는 대화를 한 번 더 해서가 아니라, 모델 호출·검색·도구 실행을 언제 멈출지 제한하지 않았을 때다.

| 비용 요인 | 줄이는 방법 |
|---|---|
| 이미 있는 전사를 다시 STT | 텍스트 입력은 STT skip |
| 회의 전체를 매번 여러 번 전송 | segment chunk 요약을 cache |
| 항상 외부 검색 | 필요성 router가 있을 때만 retrieval |
| 무제한 tool loop | 최대 tool call·시간·결과 수 제한 |
| 모든 단계에 상위 모델 | 설계/난이도높은 판단만 상위, 반복 실행은 Luna/local |
| 오류를 재시도만 함 | 파싱·Schema·권한 오류는 코드로 즉시 중단 |

수업에서는 `max_tool_calls`, timeout, 입력 길이, provider, model, fallback 이유를 결과에 기록한다. 정확한 원화 비용은 강의 당일의 공식 요금표와 실제 token usage로 다시 계산한다.

## 11. 일반 사용자에게 선물하는 순서

### 설치 전

1. 지원 OS와 최소 메모리를 적는다.
2. 음성 처리가 필요한지, 텍스트만 쓸지 묻는다.
3. 로컬 모델·API·개인 구독형 중 어느 경로를 쓸지 정한다.
4. 회의 녹음 동의와 보관 기간을 확인한다.
5. 외부 게시·발송이 기본 금지임을 설명한다.

### 가장 안전한 첫 실행

```bash
cd desktop-app/meeting-intelligence
docker compose up --build
```

브라우저에서 `http://127.0.0.1:8766`을 연다.

1. “연습 결과(fixture)” provider를 선택한다.
2. 제공된 예시 TXT를 넣는다.
3. 산업 맥락과 회의 목적을 두 줄로 적는다.
4. 실행 후 `provider_requested`, `provider_used`, `external_write=false`를 확인한다.
5. 아무 출력이나 원문 segment ID 두 개를 대조한다.
6. 승인 전까지 초안이며, 승인 후에도 외부 발송은 되지 않는다.

### 일상 사용

```text
1. 입력 유형 선택
2. 파일/텍스트와 참석자 정보 입력
3. 산업 맥락·기존 맥락·용어집 입력
4. 필요한 결과 선택
5. 미리보기 실행
6. 원문 근거 대조
7. 승인·수정·거절
8. Markdown·이메일 초안 내려받기
```

### 복구

| 증상 | 사용자에게 보여 줄 메시지 | 복구 |
|---|---|---|
| 음성 STT 실패 | “음성을 전사하지 못했습니다” | 코덱 확인·TXT 입력으로 전환; 다른 전사로 자동 대체 금지 |
| Ollama 연결 실패 | “로컬 모델이 준비되지 않았습니다” | `ollama list`, `ollama serve`; 연습 결과로 복귀 |
| API 모델 미허용 | 요청·실제 provider와 오류 코드 표시 | 키/프로젝트 권한 확인; 숨은 fallback 금지 |
| JSON 형식 오류 | “결과 구조가 올바르지 않아 HOLD합니다” | 1회 재파싱 후 fixture 또는 사람 검토 |
| 없는 근거 ID | `UNKNOWN_EVIDENCE` | 해당 항목 삭제·수정 후 재검증 |
| 외부 연결 없음 | “게시 계획만 만들었습니다” | Markdown·이메일 초안까지 사용 |

## 12. 현재 구현과 남은 Gap

### 저장소에 구현된 핵심

- Google Meet 형식 텍스트, ClovaNote TXT, 음성 파일의 세 입력 경로
- exactly-one 입력 계약과 공통 `TranscriptEnvelope`
- `DomainContext`와 `MeetingRecord`
- 고정 Workflow, single LLM, 제한된 Agent rule router 비교
- fixture·Ollama·Codex CLI·Claude CLI·선택적 OpenAI API provider
- 근거 ID 검증과 승인·수정·거절
- Markdown·이메일 초안·Notion/Confluence/email `integration_plan`
- 모든 외부 쓰기 금지, `external_write=false`

### 수업 종료 시점에도 의도적으로 남는 항목

| Gap | 왜 자동화하지 않는가 | 다음 단계 |
|---|---|---|
| 실제 Notion/Confluence 게시 | 외부 쓰기·권한·실수 위험 | 별도 write adapter + 2차 승인 + audit log |
| 실제 이메일 발송 | 수신자·첨부·외부 발송 위험 | draft 저장 후 mail client에서 사람 발송 |
| 실제 MCP 자동 조회 | 조직별 접속·권한·민감정보 정책이 다름 | read-only sandbox에서 소스별 적합성 테스트 |
| 음성 화자 실명 자동 매핑 | 오인식 시 참석자 의견이 바뀐 | diarization + 사람 매핑 UI |
| live API/STT Run All | 비용·네트워크·모델 다운로드가 필요 | 명시적 opt-in 스위치로만 실행 |
| 생성 결과의 완전한 사실성 | LLM의 본질적 불확실성 | 근거 검증·Golden Set·사람 책임 |

이 표의 Gap은 실패가 아니라 수업용 안전 경계다. 실제 조직에 선물할 때는 각 조직의 보안·법무·데이터 정책을 적용해야 한다.

## 13. 완료 판정

다음을 모두 보여 줄 수 있으면 일반 사용자에게 첫 버전을 전달할 수 있다.

- 세 입력 중 하나를 고르면 공통 transcript가 된다.
- 산업 맥락과 기존 맥락을 사용자가 입력할 수 있다.
- 요약·구성원 관점·To-do·인사이트가 구조화된다.
- 각 주요 항목을 원문 segment ID로 돌아가 확인할 수 있다.
- 없는 근거·담당자·기한은 `HOLD`된다.
- 사람이 승인·수정·거절할 수 있다.
- Markdown과 이메일 초안은 만들어지지만 외부로 자동 발송되지 않는다.
- 실패했을 때 원인과 복구 경로가 화면과 결과 파일에 남는다.
