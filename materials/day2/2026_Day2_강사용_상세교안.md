## 핵심 아키텍처 설명

```text
Google Meet text ─┐
ClovaNote TXT    ─┼─→ Input Adapter ─→ TranscriptEnvelope ─┐
Audio            ─┘        (필요한 경우만 STT)     │
                                                     ├─→ DomainContext
                                                     ├─→ Retrieval Policy
                                                     │
                                                     ▼
                                          고정 분석 Workflow
                                          요약·관점·To-do·인사이트
                                                     │
                                                     ▼
                                          Evidence/Schema Validator
                                                     │
                                                     ▼
                                          LangGraph Human Gate
                                                     │
                                                     ▼
                                    MD·email draft·integration plan
                                    external write = false
```

### 일반인에게 설명할 비유

- LLM은 글을 읽고 쓰는 전문가다.
- Workflow는 미리 정한 체크리스트다.
- Agent는 상황을 보고 허용된 서류함과 도구 중 무엇을 쓸지 고르는 비서다.
- Human Approval은 외부 저장·발송 전 사용자가 결정하는 단계다.

비유는 시작에만 쓰고, 이후에는 실제 코드 용어 `adapter`, `schema`, `router`, `validator`, `interrupt`로 연결한다.

### 정확한 구분

| 상황 | 기본 선택 | 이유 |
|---|---|---|
| 주어진 transcript 하나를 요약 | LLM | 파일·도구 선택이 필요 없음 |
| 항상 같은 순서로 요약·검증·승인 | Workflow | 순서가 고정되어 있음 |
| 입력 형태에 따라 STT 여부 판단 | rule router | 간단한 if/else가 더 싸고 안정적 |
| 요청이 모호해 어느 사내 소스가 필요한지 판단 | 제한된 Agent | 맥락·목표·정책을 함께 봐야 함 |
| 회의록을 이메일로 발송 | 소프트웨어 + 사람 승인 | LLM의 글쓰기와 외부 행동 권한은 별개 |

## 1차시 · 회의 Agent 전체 지도

### 수강생의 질문

> 요약에 LLM을 쓰면 모두 Agent인가?

### 50분 진행

| 구간 | 형태 | 내용 |
|---|---|---|
| 00~07분 | 강사 시연 | 세 입력 결과, 근거 이동, HOLD, draft |
| 07~20분 | 이론 | LLM·Workflow·rule router·Agent·외부 행동 구분 |
| 20~29분 | 강사 시연 | 같은 요청을 `workflow|llm|agent|auto`로 비교 |
| 29~38분 | 설계 활동 | 세 사용자 상황을 결정 트리로 분리 |
| 38~47분 | 코드 실행 | 아키텍처·router 결과 JSON 생성 |
| 47~50분 | 확인 | 선택 mode와 이유 확인 |

### 두괄식 메시지

> 요약은 LLM, 순서와 안전은 Workflow, 상황별 선택은 Agent에 둡니다. 역할을 나눌수록 비용과 오류를 설명하기 쉬워집니다.

### 설계 활동

| 사용자 요청 | 선택 | 근거 |
|---|---|---|
| “이 TXT만 요약해 줘” | single LLM | 외부 정보·도구 선택 불필요 |
| “업로드하면 항상 같은 양식으로 만들어 줘” | fixed workflow | 고정 단계 |
| “필요하면 최근 기획서를 찾아 비교해 줘” | bounded agent | 검색 필요성·소스 선택이 필요 |

이 활동은 설계 활동이다. 뒤의 JSON 생성과 test만 코드 실습으로 부른다.

### 코드 실습

1. Notebook의 1차시 cell을 실행한다.
2. `auto` router에 Google Meet text·Clova TXT·audio 입력을 각각 전달한다.
3. 텍스트에서 STT를 선택하는 오류를 발생시켜 test로 막는다.
4. 결과에 `mode_requested`, `mode_used`, `reason`이 있는지 확인한다.

### 복구

- mode가 이해되지 않으면 Agent를 빼고 fixed workflow만 먼저 그린다.
- 코드 실행이 안 되면 제공된 아키텍처 JSON을 읽고 `decision_reason`을 확인한다.

## 2차시 · 세 가지 입력과 STT 선택

### 수강생의 질문

> 파일 형식이 다른데 어떻게 같은 요약 코드를 쓸 수 있는가?

### 50분 진행

| 구간 | 형태 | 내용 |
|---|---|---|
| 00~10분 | 이론 | adapter·contract·segment·speaker·timestamp |
| 10~20분 | 강사 시연 | Meet·Clova·audio 입력 비교 |
| 20~45분 | 코드 실습 | exactly-one 검증·정규화·실패 test |
| 45~50분 | 확인 | 세 결과의 공통 Schema 대조 |

### 핵심 개념

- Adapter: 서로 다른 입력을 공통 언어로 바꾸는 번역기
- Contract: 다음 코드가 기대할 수 있는 필수 형식
- Segment: 근거로 다시 찾아갈 수 있는 발화 단위
- exactly-one: Meet·Clova·audio 중 하나만 받는 입력 규칙

### 강사 시연

1. Google Meet text와 참석자 정보를 넣고 `source_mode=google_meet_text`를 보여 준다.
2. ClovaNote TXT를 넣고 화자/시각 유무에 따라 `null`이 남는 것을 보여 준다.
3. 음성 입력은 강사가 검토한 WAV·TXT fixture 쌍으로 전사 metadata와 segment를 보여 준다.
4. `FASTER_WHISPER_LIVE_OPT_IN=1`이 없을 때 선택 Live 경로가 `LOCAL_STT_LIVE_OPT_IN_REQUIRED`로 건너뛰는 것을 보여 준다.
5. Meet text와 audio를 동시에 넣어 `SOURCE_MODE_MIXING_FORBIDDEN`을 보여 준다.

### 코드 실습

1. 세 입력 fixture를 각각 `SourceInput`으로 만든다.
2. `normalize_source()`를 실행해 `TranscriptEnvelope`을 만든다.
3. 모든 segment의 ID가 유일한지 확인한다.
4. 시각과 화자가 없는데 가짜로 만들어지지 않는지 확인한다.
5. 기본 `reviewed_transcript_fixture`와 선택 `faster-whisper`의 `source_mode`를 비교한다.
6. Live 의존성·모델 오류가 `LOCAL_STT_DEPENDENCY_MISSING`, `LOCAL_STT_MODEL_OR_RUNTIME_UNAVAILABLE`로 구분되는지 확인한다.

### 복구

- TXT 파싱 실패: 인코딩·화자 패턴을 보여 주고 일반 text mode로 복귀한다.
- 참석자 대응 실패: 실명을 추측하지 않고 `unknown_01`로 남긴다.

## 3차시 · 도메인 맥락과 MCP 정책

### 수강생의 질문

> AI가 산업 용어와 지난 회의를 알게 하려면 어디까지 읽게 해야 하는가?

### 50분 진행

| 구간 | 형태 | 내용 |
|---|---|---|
| 00~12분 | 이론 | context·retrieval·MCP·목적 제한 |
| 12~22분 | 강사 시연 | 맥락 없음 vs 용어집·기존 결정 주입 |
| 22~42분 | 코드 실습 | `DomainContext`·`RetrievalPolicy`·read-only plan |
| 42~47분 | 실패 확인 | 과도한 기간·범위·출처 없음 차단 |
| 47~50분 | 확인 | 이번 요청에 필요한 최소 맥락 확인 |

### Prompt Engineering 기본기

Prompt를 길게 쓰는 것이 목표가 아니다. 다음 순서로 누락 없는 계약을 만든다.

1. 역할: 회의 기록 초안 작성자
2. 목표: 원문에 근거한 `MeetingRecord`
3. 입력: transcript·domain context·retrieved context
4. 제약: 없는 담당자·기한·의도 생성 금지
5. 출력: JSON Schema와 evidence ID
6. 예외: 부족하면 추측 대신 `needs_confirmation`

### MCP 정책

```text
외부 맥락이 필요한가?
  ├─ 아니오 → transcript + DomainContext만 사용
  └─ 예
      → 어느 서비스/공간/기간/검색어가 필요한지 제안
      → 사람의 조회 승인
      → read-only로 최대 5개만 조회
      → 출처를 함께 저장
```

이 차시에서는 실제 사내 MCP를 연결하지 않는다. 조직별 인증·권한·데이터 정책이 다르므로 read-only simulated plan을 코드로 만들고 검증한다. 이는 웹사이트 구경이 아니라 정책 객체와 test를 만드는 코드 실습이다.

### 코드 실습

1. 산업·목적·용어집·기존 맥락·제약·톤을 `DomainContext`로 만든다.
2. “최근 14일, 지정 공간, read-only, 최대 5개, 출처 필수”를 `RetrievalPolicy`로 만든다.
3. 외부 맥락이 불필요한 요청은 tool call 0회로 끝나는지 확인한다.
4. 90일·전사 검색·출처 없음을 넘겨 차단 코드를 확인한다.

### 복구

- MCP가 없으면 사용자가 직접 입력한 `prior_context`만 쓴다.
- 출처가 없는 검색 결과는 요약 근거로 쓰지 않는다.

## 4차시 · MeetingRecord Schema

### 수강생의 질문

> 회의록이 그럴듯한 글이 아니라 검증 가능한 데이터가 되려면 무엇이 필요한가?

### 50분 진행

| 구간 | 형태 | 내용 |
|---|---|---|
| 00~10분 | 이론 | Schema·nullable Field·Evidence·Well-being 제한 조건 |
| 10~20분 | 강사 시연 | 좋은 결과·근거 누락·임의 담당자 결과 비교 |
| 20~43분 | 코드 실습 | `MeetingRecord` 생성·검증·실패 Case |
| 43~48분 | 실패 확인 | `s999`·없는 owner·임의 due date |
| 48~50분 | 확인 | 결과 항목에서 원문 segment로 돌아가기 |

### 필수 결과

- 회의 목적과 기존 맥락
- 핵심 요약과 결정 사항
- 구성원별 발언에서 확인된 관점
- owner·due date·evidence가 있는 To-do
- 단기·중기·장기 인사이트
- 업무 편중·미합의를 단정 없이 표시하는 well-being 확인 항목

“구성원의 생각”은 내면 추측이 아니다. 실제 발언에서 확인된 관점·우려·제안만 기록하고, 확인할 수 없는 값은 `null` 또는 `CONFIRM_REQUIRED`로 둔다.

### 코드 실습

1. 같은 transcript로 `MeetingRecord`를 만든다.
2. 모든 요약·결정·관점·To-do·인사이트의 evidence ID를 known segment 집합과 대조한다.
3. 원문에 없는 담당자·기한을 넣어 validator가 차단하는지 확인한다.
4. 알 수 없는 값을 `null`로 둔 Expected Output과 임의로 채운 위험 결과를 비교한다.
5. `04_meeting_record_contract.json`에서 실제 `MeetingRecord` Field와 Evidence Validation 결과를 확인한다.

### 복구

- Schema 오류: LLM을 다시 부르기 전에 Python validator의 field·type·evidence 오류를 확인한다.
- 근거 누락: 결과를 자동 보완하지 않고 원문 대조를 요청한다.
- well-being: 개인 성향·건강 상태를 진단하지 않고 업무 부하 신호와 확인 질문만 남긴다.

## 5차시 · Coding Agent Workflow

### 수강생의 질문

> 상위 모델과 어떤 대화를 나누어야 세 입력을 빠뜨리지 않고 실제 소프트웨어로 만들 수 있는가?

### 50분 진행

| 구간 | 형태 | 내용 |
|---|---|---|
| 00~10분 | 이론 | Scenario tree·Harness·완료 조건·독립 리뷰 |
| 10~20분 | 강사 시연 | 막연한 한 문장 요청과 단계형 요청 비교 |
| 20~38분 | 코드 실습 | Codex 작업 명세로 최소 vertical slice와 test 생성 |
| 38~45분 | 강사 시연 | Claude Code Cross-Review와 누락 조건 확인 |
| 45~50분 | 확인 | Diff·Focused Test·Human Merge Decision |

### 대화 순서

1. 일반 사용자의 Meet·ClovaNote·audio 시작 상황을 먼저 정의한다.
2. 각 상황의 성공·실패·복구와 공통 결과 계약을 표로 만든다.
3. 외부 저장·발송 금지, Secret 비노출, Fixture 완주를 작업 제한으로 고정한다.
4. 저장소의 관련 파일·test·더티 변경을 읽기 전용으로 진단하게 한다.
5. 한 번에 하나의 Vertical Slice만 구현하고 Happy Path·Boundary Test를 함께 요구한다.
6. 다른 모델의 리뷰와 사람의 diff 확인 뒤에만 merge한다.

숨은 chain-of-thought를 요구하지 않는다. 대신 `선택지 → 선택 기준 → 선택 결과 → 근거 → 중단 조건`이 보이는 decision tree를 요청한다.

### 코드 실습

1. `materials/day2/Codex_Claude_대화_시나리오.md`의 단계형 Prompt를 현재 저장소에 맞게 채운다.
2. Codex에 허용 파일·완료 조건·금지 행동·focused test를 함께 전달한다.
3. Meet 입력 하나의 최소 변경을 만들고 diff를 읽는다.
4. ClovaNote·audio·미승인 외부 서비스 저장·게시·발송 Case를 test로 확장한다.
5. Claude Code 또는 별도 Codex session에는 구현이 아니라 누락·권한·fallback만 독립 리뷰하게 한다.

### 복구

- 상위 모델이 너무 많이 바꾸면 허용 경로와 한 Turn 한 Role로 범위를 줄인다.
- test를 약화하거나 `.env`를 바꾸면 diff를 폐기하고 작업 명세부터 수정한다.
- Claude 로그인이 없으면 제공된 리뷰 Prompt를 읽고 강사가 동일 체크리스트로 리뷰한다.

> 무료·구독형·API 모델을 어떻게 바꾸어도 같은 결과와 실패 이유를 남길 수 있는가?

| 역할 | 권장 | 이유 |
|---|---|---|

Codex 앱에서 “5.6 Sol ultra”가 실제 선택지로 보일 때만 해당 조합을 사용한다. API에서는 계정이 허용하는 실제 모델 ID와 reasoning effort를 진단하고, 사용하지 않은 모델을 사용했다고 기록하지 않는다.

### 비용 제한

- 전사가 있는 입력은 STT를 skip한다.
- 외부 맥락이 필요한 경우에만 retrieval한다.
- 도구 호출 수·timeout·검색 결과 수·token budget을 제한한다.
- 없는 field는 LLM 재시도 전에 Python validator로 걸러낸다.
- 도메인 용어집과 고정 정책은 cache한다.

### 코드 실습

1. `06_provider_diagnostics.json`의 installed·auth·live opt-in을 구분한다.
2. 같은 prompt를 fixture와 선택 provider로 실행해 `provider_requested`, `provider_used`, `model`, `fallback_reason`을 비교한다.
3. Ollama `qwen3:4b`는 로컬 실행 결과만 성공으로 표시한다.
4. OpenAI는 `OPENAI_LIVE_OPT_IN=1`과 key·project·model 가용성을 확인한 경우만 호출한다.
5. fallback off에서 안정된 `HOLD`와 error code가 남는지 확인한다.

### 복구

- 로컬 모델 실패: fixture로 복귀하되 `fallback_reason`을 보여 준다.
- OpenAI 접근 실패: auth·project·model·timeout을 구분하고 live 호출을 끈다.
- parser 실패: raw 문장을 성공과 혼동하지 않고 `HOLD`한다.

## 7차시 · LangGraph · Human Review

### 수강생의 질문

> 그럴듯한 결과를 왜 Graph에서 멈추고 사람이 승인해야 하는가?

### 50분 진행

| 구간 | 형태 | 내용 |
|---|---|---|
| 00~10분 | 이론 | state·node·edge·conditional edge·checkpoint·interrupt |
| 10~20분 | 강사 시연 | READY·HOLD·approve·edit·reject |
| 20~43분 | 소프트웨어 실습 | Interrupt·Checkpoint·Command Resume·Conditional Edge |
| 43~48분 | 실패 확인 | `s999`·빈 evidence·수정본 재검증 |
| 48~50분 | 확인 | 외부 서비스 저장·게시·발송이 끝까지 `false`인지 확인 |

### 설명 순서

1. State는 현재 업무 상태를 담는 서류첩이다.
2. Node는 한 번에 하나의 일을 하는 단계다.
3. Edge는 다음 단계로 가는 길이다.
4. Conditional edge는 검증 결과에 따라 길을 바꾼다.
5. Interrupt는 AI가 멈추고 사람의 판단을 받는 지점이다.
6. Checkpoint는 재시작할 수 있는 상태 기록이다.

LangGraph를 “Agent를 자동으로 만드는 마법”으로 설명하지 않는다. 업무 순서와 중단·복구·승인을 코드로 표현하는 상태 기계로 설명한다.

### 코드 실습

1. `build_interruptible_meeting_graph()`로 Checkpointer가 포함된 Graph를 만든다.
2. `learner_interrupt_start`의 `__interrupt__`와 `thread_id`를 확인한다.
3. `LEARNER_REVIEW_DECISION`에 approve·edit·reject 중 하나를 정하고 해당 thread를 한 번 재개한다.
4. `automated_regression_evidence`에서 별도 thread로 실행된 세 결정의 결과를 확인한다.
5. 수정한 edit 결과는 Evidence를 재검증하고, reject는 Draft 없이 종료하는지 확인한다.
6. `s999`를 주입해 Human Review 전 Evidence Conditional Edge에서 차단되는지 확인한다.

### 복구

- interrupt에서 멈춘 것은 오류가 아니다. 보류 상태와 재개 입력을 구분한다.
- checkpointer를 분실하면 외부 write를 재실행하지 말고 처음부터 dry-run한다.
- `READY_FOR_REVIEW`를 `APPROVED`로 해석하지 않는다.

수강생 기본은 Docker 없는 localhost App이다. 사전 제작 EXE와 PKG는 Docker Launcher이므로 Docker Desktop이 준비된 강사 PC에서만 선택 시연하고 `dist/SHA256SUMS`를 함께 확인한다. 현재 Package는 교육·내부 검증용 unsigned build다. 외부 배포 전에는 Windows code signing, Apple Developer ID signing·notarization, 업데이트·삭제·라이선스 안내가 필요하다. Codex·Claude CLI bridge는 기본 `OFF`이며 합성 데이터 강사 확장에서만 `--enable-cli-bridge`로 켠다.

### 통합 코드 실습

1. `run-local.command` 또는 `run-local.cmd`로 localhost App을 연다.
2. `예시로 바로 시작`을 누르고 fixture provider로 Meet text 입력을 완주한다.
3. ClovaNote TXT가 STT를 skip하는지 확인한다.
4. GUI 음성 입력은 live `faster-whisper`이며, `stt_mode=fixture`는 GUI 선택지가 아님을 확인한다.
5. `LIVE_STT_DEPENDENCY_MISSING`·`LIVE_STT_MODEL_UNAVAILABLE`·`LIVE_STT_FAILED`가 다른 전사 대입 없이 `HOLD`되는지 확인한다.
6. Markdown·전체 JSON을 내려받고 email은 `DRAFT_ONLY`임을 확인한다.
7. Notion·Confluence·email은 `PLAN_ONLY`, `external_write=false`인지 확인한다.
8. `08_localhost_launch.json`의 Version·Smoke·안전 경계를 확인한다.

### ToT를 수업에서 표현하는 방법

모델의 숨은 chain-of-thought를 요청하지 않는다. 대신 사람이 검토할 수 있는 결정 트리를 요청한다.

```text
입력은 무엇인가?
  ├─ Meet/Clova text → STT skip
  └─ audio → consent/audio validation/local STT

요청에 기존 자료가 필요한가?
  ├─ 아니오 → external tool 0회
  └─ 예 → read-only retrieval plan → 조회 승인

근거가 유효한가?
  ├─ 아니오 → HOLD
  └─ 예 → human review
```
