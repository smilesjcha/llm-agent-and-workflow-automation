## 온라인 수업 운영 원칙

- 모든 개인 활동은 강사 화면을 보며 각자 진행한다.
- 짝 활동, 조별 토론, 수강생 발표는 진행하지 않는다.
- 수강생의 회사 업무, 구직 상태, 개인 프로젝트 주제를 공개하도록 요구하지 않는다.
- 소프트웨어 실습 결과는 각자의 notebook·로컬 파일·Git 저장소에 남긴다.
- 질문은 채팅창으로 받는다.
- 질문할 때는 가능하면 아래 네 가지를 남기도록 안내한다.
  1. 화면에 보이는 첫 오류 문장
  2. 오류 직전에 누른 버튼이나 입력한 명령
  3. 운영체제와 Python 버전
  4. 원래 기대한 결과
- 설치가 오래 걸리면 기다리지 않고 제공된 fixture와 예제 결과로 수업을 계속한다.

## 1일차 1차시. Agent와 문제 정의

### 이 차시에서 꼭 전달할 말

> Agent를 만드는 첫 단계는 모델을 고르는 일이 아니라, 어떤 일을 어디까지 맡길지 정하는 일입니다.

### 쉽게 설명할 용어

- 생성형 AI: 학습한 패턴을 바탕으로 새로운 글·이미지·코드를 만드는 기술
- LLM: 많은 글을 학습해 다음에 올 말을 계산하는 언어 모델
- Agent: 목표를 받고 현재 상태를 보며 도구를 선택하고 결과를 확인하는 실행 구조
- Harness Engineering: 모델 주변에 지시문·도구·권한·test·기록 장치를 함께 설계하는 방식

### 개인 Ideation

먼저 자주 반복하는 일을 하나 고르게 한다.

- 입력은 무엇인가?
- 원하는 결과는 무엇인가?
- AI가 하면 안 되는 행동은 무엇인가?

예시는 강사가 먼저 실제 코드 결과로 보여준다.

> 회의 녹음 → 회의 요약과 할 일 목록 생성 / 자동 메일 발송은 하지 않음

구두 설명만으로 끝내지 않는다. 약 1분짜리 비식별 회의 음성을 넣고 transcript.json과 meeting_result.json이 생성되는 화면을 보여준다. 로컬 STT가 실패하면 같은 명령이 합성 transcript fixture를 사용하도록 준비한다. 수강생이 여기서 직접 STT를 설치할 필요는 없으며, 각자 입력·결과·금지 행동을 적는 데 집중한다.

상세 실행 순서는 [강사 회의음성 라이브 Demo 런북](./강사_회의음성_라이브데모_런북.md)을 따른다.

수강생에게 답을 발표시키거나 채팅창에 공개하도록 요구하지 않는다.

### 완료 기준

`입력 1개 + 원하는 결과 1개 + 금지 행동 1개`

## 1일차 2차시. Tool Calling과 실행 권한

### 이 차시에서 꼭 전달할 말

> 모델이 도구 사용을 제안할 수는 있지만, 실제로 실행해도 되는지는 애플리케이션이 검사해야 합니다.

### 쉽게 설명할 용어

- Tool: 파일 읽기, 검색, API 호출처럼 Agent가 사용할 수 있는 실제 기능
- Schema: 도구가 어떤 값을 받아야 하는지 정한 입력 양식
- Allowlist: 사용을 허용한 도구 목록
- Validation: 도구를 실행하기 전에 이름·인자·경로가 안전한지 확인하는 과정

### 강사 데모 순서

1. 모델 또는 planner가 `read_public_text` 호출을 제안한다.
2. Validator가 허용된 도구인지 확인한다.
3. 파일 경로가 허용된 폴더 안인지 확인한다.
4. 안전하면 실행하고, 아니면 오류 코드로 멈춘다.

### Prompt Engineering 기본기

Tool Calling Prompt는 길게 쓰기보다 다음 네 덩어리를 분명하게 둔다.

1. SYSTEM: Agent의 역할, 허용 행동, 금지 행동
2. TASK: 이번 입력과 원하는 결과
3. TOOLS: 도구 이름, 설명, 인자 schema
4. EXAMPLE: 정상 호출과 차단되어야 할 호출

모델이 만든 JSON은 실행 명령이 아니라 제안이다. Prompt가 좋아도 validator·allowlist·test를 대신할 수는 없다.

### 수강생이 이해하면 되는 기준

- 읽기 도구와 쓰기 도구의 위험은 다르다.
- 모델의 응답과 실제 실행 권한은 분리해야 한다.
- 잘못된 요청은 traceback으로 끝내지 않고 이해 가능한 오류 결과로 바꾼다.

## 1일차 3차시. 한국어 데이터와 PBL 사례

### 이 차시에서 꼭 전달할 말

> 회의 요약은 자연스럽게 쓰는 것보다 누가, 무엇을, 언제까지 해야 하는지 원문 근거와 함께 남기는 것이 중요합니다.

### 오늘 사용할 데이터 원칙

- 실제 회사 회의나 고객 정보는 사용하지 않는다.
- 공개 데이터 또는 강사가 제공한 합성 회의 데이터를 사용한다.
- 사람 이름, 금액, 이메일 등은 필요하면 가린다.
- 요약 결과가 원문의 어느 부분에서 나왔는지 evidence ID를 남긴다.

### 회의 데이터에서 뽑을 항목

- 결정된 내용
- 해야 할 일
- 담당자
- 기한
- 원문 근거
- 확신하기 어려워 사람 확인이 필요한 항목

### 한국어 업무 Prompt 기본기

- 역할: “한국어 회의 기록 보조자”처럼 한 문장으로 고정한다.
- 입력: transcript만 주지 말고 segment ID, 시각, 화자, 회의 기준일을 함께 준다.
- 출력: summary·decision·action item을 JSON schema로 고정한다.
- 금지: 원문에 없는 담당자와 기한은 추론하지 않는다.
- 근거: 모든 결정과 할 일에 evidence ID를 요구한다.
- 모호성: 확신할 수 없으면 null과 needs_review를 반환하게 한다.

### 자료 수집·데이터 확인

다음 세 파일을 공통 사례로 사용한다.

- data/meeting_sample_ko_12min.txt: 약 17분 분량의 상세 합성 회의 transcript
- data/meeting_sample_ko_12min.wav: 약 16분 57초의 다화자 합성 WAV
- data/meeting_sample_ko_12min_expected.json: 결정·Action Item·정정·needs_review의 기준 결과

Dataset Card는 data/meeting_sample_ko_12min_DATASET_CARD.md에 있다. 강사는 전체 흐름을 먼저 보여주고, 수강생은 2~3분 구간에서 결정 한 건·정정 발언 한 건·Action Item 두 건을 찾는다.

제공된 합성 회의 예시를 보고 다음 한 건을 만든다.

```json
{
  "task": "요약 초안 검토",
  "owner": "담당자 A",
  "due_date": "2026-08-25",
  "evidence_id": "seg-03"
}
```

### 강사 화면에서 확인할 순서

1. 저장소 폴더를 VS Code로 열고 `04_ollama_agent_workflow.ipynb`를 연다.

4. `probe_ollama()`로 CLI·서버·모델 상태를 JSON으로 출력한다.
5. `probe_openai()`로 SDK·키 설정 여부·live opt-in만 출력한다. 키 값은 절대 표시하지 않는다.
6. fixture/Ollama/OpenAI 중 사용할 lane을 선택한다. 직접 `provider="openai"`를 지정하면 API 실행 선택이며, Notebook Run All만 `RUN_OPENAI_LIVE=1`로 보호한다.
7. `tests/test_ollama_tool_agent.py` 여덟 개를 notebook에서 실행한다.
8. 전체 `pytest`는 점심 전 5차시 마지막에 실행한다.
9. Git·Codex·Draft PR은 notebook 실행이 끝난 사람의 선택 확장으로 둔다.

## 1일차 6차시. 무료·로컬 LLM과 adapter

### 이 차시에서 꼭 전달할 말

> 무료 소프트웨어 실습의 핵심은 모든 사람이 같은 모델 설치에 성공하는 것이 아니라, 모델이 없어도 같은 코드 계약을 끝까지 실행하는 것입니다.

5차시에서 만든 안전한 Tool Call 결과를 그대로 두고, 같은 notebook의 다음 구간에서 LangChain LCEL provider만 교체한다.

### 도구 차이

| 도구 | 쉽게 말하면 | 수업에서의 위치 |
|---|---|---|
| Ollama | 명령어와 localhost API로 모델을 실행 | 선택 소프트웨어 실습 |
| GPT-5.6 Luna | Responses API로 function/text 요청 | 키가 있는 사람의 선택 비교 |
| LM Studio | 화면에서 모델을 받고 local server를 실행 | Ollama 대안 |
| Jan | 데스크톱 기반 local API 대안 | 추가 선택지 |
| Fixture Provider | 미리 준비한 고정 응답 | 모든 수강생의 기본 fallback |

### adapter를 쉽게 설명하면

서로 다른 충전기를 하나의 멀티 어댑터에 연결하는 것과 같다. 모델마다 URL과 응답 형식이 달라도 애플리케이션에는 같은 결과 형식을 전달한다.

### 성공 기준

- Local LLM 연결 성공 또는 예상된 연결 실패
- 실패 시 `OLLAMA_UNAVAILABLE` 같은 오류 코드 확인
- Fixture Provider로 같은 다음 단계를 계속 실행
- 모델을 바꿔도 schema와 validator는 유지
- 세 provider 모두 `MeetingBrief` typed output 계약 유지

### 직접 실행할 코드

```python
fixture_chain = run_langchain_lab(transcript, provider="fixture")
ollama_chain = run_langchain_lab(
    transcript,
    provider="ollama",
    model="qwen3:4b",
    allow_fallback=True,
)
openai_chain = run_langchain_lab(
    transcript,
    provider="openai",
    model="gpt-5.6-luna",
    allow_fallback=False,
)
```

수강생은 세 결과에서 `provider_requested`, `provider_used`, `fallback_reason`, `checks`만 먼저 비교한다. OpenAI 최초 확인은 `allow_fallback=False`로 인증·권한·schema 오류를 직접 보고, 확인 후 수업 복구용으로 `True`를 쓴다. 실제 모델의 문장 품질 비교보다 schema·근거·자동 메일 금지·사람 승인 정책이 유지되는지가 우선이다.

## 1일차 7차시. LangChain·LangGraph와 사람 승인

### 이 차시에서 꼭 전달할 말

> LangGraph는 복잡해 보이는 Agent를 여러 단계로 나누고, 중간에 멈춘 뒤 같은 상태에서 다시 시작하기 위해 사용합니다.

LangChain과 LangGraph를 따로 구경하지 않는다. `Prompt → Provider → Parser → Validator`를 LangChain LCEL로 실행한 결과를 LangGraph의 State로 넘기고, 사람 결정 직전에 멈춘 뒤 같은 `thread_id`로 재개한다.

### 쉽게 설명할 용어

- State: 현재까지의 입력·결과·상태를 모아둔 작업 기록
- Node: 요약, 검증, 승인 요청처럼 한 가지 일을 하는 단계
- Edge: 다음에 어느 단계로 갈지 정하는 연결
- Checkpoint: 중간 상태를 저장한 복구 지점
- Interrupt: 사람 확인이 필요할 때 실행을 잠시 멈추는 기능

### 40분 운영과 연결고리

| 시간 | 구분 | 강사 화면 | 수강생이 직접 할 일 | 완료 증거 |
|---|---|---|---|---|
| 15:40-15:48 | 개념 강의 | LCEL의 `|`, State·Node·Edge·Checkpoint·Interrupt | 코드에서 각 개념의 위치 표시 | 실행 순서 메모 |
| 15:48-15:55 | 강사 코드 시연 | fixture LCEL 실행과 Pydantic 결과 | 입력·출력 schema 확인 | `schema_valid=true` |
| 15:55-16:05 | 소프트웨어 실습 1 | notebook LCEL 셀 | Prompt 한 줄 수정 후 셀 실행 | typed JSON |
| 16:05-16:12 | 강사 코드 시연 | 최초 invoke가 review에서 멈추는 장면 | `__interrupt__` payload 확인 | 승인 질문·근거 |
| 16:12-16:18 | 소프트웨어 실습 2 | 같은 thread를 `Command(resume=...)`로 재개 | approve·edit·reject 실행 | 세 terminal state |
| 16:18-16:20 | 실행 확인 | trace와 Vercel 결과 화면 | 생성 JSON 존재 확인 | local JSON·다운로드 파일 |

### 직접 사용할 파일

| 파일 | 구현할 기능 | 수강생이 바꿔볼 최소 범위 |
|---|---|---|
| `materials/day1/07_langchain_langgraph_workflow.ipynb` | 전체 흐름을 셀 단위로 실행 | Prompt 한 줄·사람 결정 값 |
| `src/langchain_lab.py` | Prompt·Provider·Parser·Policy를 LCEL로 조립 | `provider=fixture/ollama/openai` |
| `src/langgraph_lab.py` | StateGraph·조건 분기·interrupt·resume | `decision=approve/edit/reject` |
| `src/workflow_service.py` | LCEL→Graph→평가→trace를 한 번에 실행 | decision·output directory |
| `tests/test_langchain_langgraph_lab.py` | 정상·수정·거절 정책을 자동 검증 | assertion과 실패 메시지 확인 |

### 강사가 먼저 실행할 명령

```bash
python -m src.langchain_lab --provider fixture
python -m src.langgraph_lab --decision all
python -m pytest -q tests/test_langchain_langgraph_lab.py
```

전체 서비스 흐름은 다음 명령으로 확인한다.

```bash

python -m src.workflow_service --decision reject --out output/day1-workflow-reject
```

정상 경로는 `READY_FOR_EXPORT/READY`, 거절 경로는 `REJECTED/HOLD`여야 한다. 두 경로 모두 `automatic_email=false`이고 외부 쓰기는 없어야 한다.

### 사람 검토 결과

- 승인: 그대로 다음 단계로 이동
- 수정: 사람이 고친 결과로 이동
- 거절: 발행하지 않고 종료
- 재개: 저장된 checkpoint에서 다시 시작

### 소프트웨어 실습

같은 초안에 대해 `approve`, `edit`, `reject` 세 입력을 바꿔 실행한다. 화면 공유나 발표는 하지 않고 각자의 notebook에서 `READY_FOR_EXPORT`, 수정된 summary, `REJECTED`를 확인한다. 설치가 막히면 `07_langchain_langgraph_workflow.executed.ipynb`와 저장된 JSON으로 같은 상태 전이를 추적한다.

브라우저 결과 확인은 실행을 대체하지 않는다. Python 결과가 생성된 뒤 `https://web-demo-five-sigma.vercel.app`에서 승인·수정·거절을 눌러보고 JSON을 내려받는다. 네트워크가 막히면 `web-demo`에서 `python -m http.server 4173`을 실행한다.

## 1일차 8차시. STT와 LangSmith

### 이 차시에서 꼭 전달할 말

> STT가 틀리면 LLM은 틀린 문장을 더 그럴듯하게 정리할 수 있습니다. 그래서 입력 품질과 실행 기록을 함께 봐야 합니다.

### STT 운영 방식

- Google Meet 등에서 이미 전사와 회의 노트를 제공하면 그 결과를 먼저 활용한다.
- Local STT는 서비스 전체를 다시 만들기보다 segment·timestamp·품질 flag를 코드로 검사하는 최소 소프트웨어 실습으로 진행한다.
- `faster-whisper`는 Python 통합 경로, `whisper.cpp`는 가벼운 CLI 대안으로 소개한다.

### STT 품질에서 볼 것

- 빈 텍스트
- 같은 문장의 비정상 반복
- 이름·숫자·날짜 오류
- timestamp 누락
- 사람이 다시 들어야 하는 구간

### LangSmith를 쉽게 설명하면

LangSmith는 Agent가 어느 단계에서 어떤 입력과 출력을 만들었는지 확인하는 실행 기록 화면이다.

수강생에게는 다음 네 질문만 기억하게 한다.

1. 어느 단계가 가장 느렸는가?
2. 어느 단계에서 오류가 발생했는가?
3. 사람이 가장 많이 수정한 필드는 무엇인가?
4. 다음 버전을 배포해도 되는가?

### READY와 HOLD

- READY: schema, 근거, 안전, 지연시간 기준을 모두 통과
- HOLD: 하나라도 기준을 만족하지 못해 수정이 필요한 상태

LangSmith 계정이나 네트워크가 없으면 local JSONL 기록과 pytest 결과로 같은 판단 흐름을 설명한다.

### 소프트웨어 실습 실행 순서

1. `src.meeting_demo.py`로 합성 WAV 또는 제공 transcript를 읽어 `transcript.json`을 만든다.
2. `detect_quality_flags`로 빈 텍스트·반복·깨진 문자와 fallback 여부를 검사한다.
3. `src.workflow_service.py`를 실행해 LCEL·Graph·release gate를 연결한다.
4. `src.observability_lab.py`의 `LocalTraceRecorder`가 node별 상태와 latency를 `trace.json`에 남기는지 확인한다.
5. approve 결과는 READY, reject 결과는 HOLD인지 test로 확인한다.
6. LangSmith 계정이 준비된 강사만 비식별 summary를 선택 업로드한다. transcript와 API key는 화면과 trace에서 제외한다.

```bash
python -m src.meeting_demo \
  --audio data/demo_meeting.wav \
  --transcript data/demo_meeting_transcript.txt \
  --out output/day1-demo \
  --model tiny --device cpu --compute-type int8
python -m src.workflow_service --decision approve --out output/day1-workflow
python -m pytest -q tests/test_observability_workflow.py
```

완료 증거는 `transcript.json`, `meeting_result.json`, `trace.json`, `workflow_result.json`, `READY/HOLD` 판단이다. LangSmith를 사용하지 못해도 동일한 trace·평가 계약을 로컬에서 끝까지 실행할 수 있다.

## 처음 듣는 사람에게 바꿔 말할 표현

| 어려운 표현 | 수업에서 먼저 쓸 쉬운 표현 |
|---|---|
| Agentic Workflow | 여러 단계를 스스로 이어가는 실행 흐름 |

| Trace | 한 요청이 지나간 단계별 실행 기록 |
