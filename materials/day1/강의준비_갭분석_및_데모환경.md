# 1일차 강의 준비 갭 분석과 데모 환경

## 결론

1일차의 핵심은 홈페이지 탐색이 아니라 `VS Code/Jupyter → Ollama 상태 진단 → Tool Calling → LangChain LCEL → LangGraph interrupt/resume → STT·trace → 브라우저 결과`를 실제로 실행하는 것이다. 4차시부터 같은 입력과 결과 계약을 이어 쓴다. Vercel은 Python framework를 대체하지 않고, Python에서 생성한 승인·수정·거절 결과를 검토하고 JSON으로 내려받는 Day 1 결과 UI로 사용한다.

## 수업 전에 반드시 끝낼 것

완료:

1. 원격 GitHub `main`에 기능 단위 커밋을 순서대로 push했다.
2. 로컬 Python 3.12에서 23 tests와 whitespace 검사가 통과했다.
3. `data/demo_meeting.wav`를 fixture fallback까지 포함해 사전 실행했다.
4. 270장 PPT와 270쪽 PDF의 전체 렌더·오버플로·중복 메시지 검사를 마쳤다.
5. 별도 Python 3.12 가상환경에서 Ollama Agent·LangChain·LangGraph Notebook Run All과 23 tests를 통과했다.
6. LCEL typed output, approve/edit/reject terminal state, local trace, READY/HOLD 결과를 JSON으로 저장했다.
7. Vercel 결과 UI를 배포하고 HTTP 200·브라우저 조작·콘솔 오류 없음까지 확인했다.
8. `faster-whisper`의 `tiny` 모델로 66초·약 17분 WAV를 실제 전사했다. 짧은 파일은 `READY`, 상세 파일은 깨진 문자 탐지로 `HOLD`가 나오는 것을 확인했다.

강의 전 남은 확인:

1. 실제 Ollama 시연을 할 경우 macOS 앱을 설치하고 `ollama run qwen3:4b`로 모델을 전날 내려받는다. 현재 강사 PC에는 Ollama가 설치되어 있지 않다.
2. 교육용 PR 한 건을 만들고 diff·CI·리뷰 화면을 캡처한다. 이 경로는 4차시 빠른 수강생의 선택 확장이다.
3. Codex GitHub Code Review를 사용할 계정과 repository 연결 여부를 확인한다.
4. 수업에서 `small` STT 모델을 쓸 경우 전날 미리 내려받아 cold start를 없앤다. 당일 안정성 점검은 이미 검증한 `tiny`로 한다.
5. LangSmith에는 합성 데이터만 보내고 API key·project name을 화면에서 가린다.
6. 발표 모드에서 터미널 글자 크기, 브라우저 알림, 사용자 홈 경로가 보이지 않는지 확인한다.

## 강사 당일 15분 사전 점검

아래 순서까지만 통과하면 1일차 소프트웨어 실습을 진행할 수 있다.

~~~bash
source tmp/lang-labs-venv/bin/activate

  materials/day1/04_ollama_agent_workflow.ipynb \
~~~

## Vercel을 언제 쓰는가

Day 1에는 Python 실행 결과를 읽고 사람 결정을 바꾸는 정적 UI로만 쓴다. 다음 조건을 모두 만족해야 한다.

- 로컬 pipeline과 unit test가 먼저 통과한다.
- 화면은 합성 meeting_result.json만 읽는다.
- 고객정보·실제 회의·API key를 브라우저에 보내지 않는다.
- 외부 발행·메일·DB 쓰기 기능이 없다.
- local UI·JavaScript 검사·HTTP 응답을 확인한 뒤 Production을 연다.

배포는 필수 성공 조건이 아니다. 계정·네트워크가 막히면 동일한 `web-demo`를 `python -m http.server 4173`으로 열고 JSON을 내려받는다. 수업의 필수 학습은 Python의 LCEL·StateGraph·test이며 웹은 결과 확인 계층이다.

## Codex와 Vercel 데모를 만들 때의 대화 예시

강사:

~~~text
Objective: 합성 meeting_result.json을 읽기 전용으로 보여주는 작은 웹 Demo를 만들어줘.
Scope: web-demo 폴더만 생성.
Data: Python이 만든 web-demo/public/demo-data.json만 사용.
Do not: API key, 실제 회의, 외부 쓰기, 메일, DB를 추가하지 말 것.
UI: Summary, Decisions, Action Items, Evidence, Human Review 상태.
Verify: build 성공, 빈 데이터·잘못된 JSON 처리 test.
Deliver: 계획, diff, 실행 명령, test와 build 결과.
~~~

Codex가 계획을 제안하면 강사는 다음을 확인한다.

1. web-demo 밖의 파일을 바꾸지 않는가?
2. 합성 JSON만 client에 포함되는가?
3. 잘못된 JSON과 빈 Action Item 예외가 있는가?
4. 배포 전에 local build가 통과하는가?
5. Python 실행 결과와 브라우저 UI의 역할이 분리되어 있는가?

## Vercel 캡처 순서

1. Codex 작업 계약 입력
2. 생성된 web-demo diff
3. local test와 build
4. approve·edit·reject 브라우저 조작
5. 결과 JSON 다운로드
6. Vercel Production URL
7. HTTP 200과 브라우저 console 오류 없음

Day 1 본편에서는 7차시 마지막에 결과 UI를 짧게 확인한다. 배포 설정 설명은 강사용 교안에 두고, 수강생은 이미 배포된 URL 또는 localhost 중 하나를 사용한다.
